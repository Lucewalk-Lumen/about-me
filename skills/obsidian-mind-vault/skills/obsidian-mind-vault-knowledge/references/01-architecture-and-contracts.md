# 01 · 架构与契约

## 1. 四层模型

| 层 | 实现形态 | 职责 | 关键约束 |
|----|---------|------|---------|
| ① 库本体 | Markdown + 元数据 + 双链 | 可移植、可版本控制、可在编辑器里浏览 | 用户内容与模板基础设施的切分由库根清单声明 |
| ② 钩子管道 | 由宿主在生命周期事件上调用的小脚本，**无构建步骤** | 会话开始 / 每条消息 / 写后 / 压缩前 / 每轮回复后 | 按**文档化事件名**分支，绝不按宿主专有 payload 字段分支 |
| ③ 语义检索层 | 独立 CLI + SQLite 索引 + 服务端，全部绑定到清单里的**命名索引** | 按需检索，秒级且无模型调用 | 编辑器与检索引擎共用**同一份忽略清单**（以编辑器的忽略配置为唯一真相源） |
| ④ 跨仓服务层 | 把库变成服务，让别的仓库的会话可检索 / 阅读 / 沿图扩展 / 回写 | 四个服务面 | 身份由客户端握手派生，绝不信任调用方声明 |

> 第 ④ 层是改变系统形态的那一层。前三层都假设「agent 就坐在库里」；第 ④ 层去掉了这个假设，于是「谁在提问」成为一等公民。

## 2. 唯一协调点

库根有一份机器可读清单文件，**每一层都读它**。它回答八个问题：

| 问题 | 字段族 |
|------|--------|
| 这是哪个版本的模板？ | `version`、`released`、`version_fingerprints` |
| 检索索引叫什么？ | `qmd_index`、`qmd_context`、`qmd_min_version` |
| 哪些文件是模板基础设施？ | `infrastructure[]` |
| 哪些文件是用户内容？ | `user_content_roots[]`、`scaffold{}` |
| 每类笔记的必填元数据是什么？ | `frontmatter_required{}` |
| 服务对外暴露哪些笔记、记忆住哪里？ | `mcp_exposed_roots[]`、`mcp_never_expose[]`、`memory_root`、`mcp_inbox` |
| 常驻上下文可以花多少字节？ | `eager_layer_budget_bytes`、`eager_layer_instruction_budget_bytes`、`listing_collapse_threshold` |
| 派生推理跑在哪个模型上？ | `reason.model`（未设即用用户 CLI 默认值） |

**关键事实**：索引名字段被**五个独立调用方**读取；任何一处取值不一致都会**静默失败**（表现为检索无结果，而不是报错）。模板出厂时该字段为空，由库文件夹名派生，以保证同机多库不共享索引存储。

## 3. 责任划分（全系统最重要的边界）

> **过程式代码拥有环境。agent 拥有内容。**
> 两侧只在小而明确的交接点相遇，**谁都不越过边界**。

- 代码侧负责：分类、校验、索引、生命周期注入、预算裁剪
- agent 侧负责：写笔记、归档、建链、起草
- 交接点只有两个：① 代码把上下文注入会话；② agent 读完库后写入

这条边界同时解释了几件事：为什么路由逻辑放在**可编辑的操作手册**里而不是脚本里（保持钩子无观点）、为什么指令文件里不写计数（会腐烂）。

## 4. 四条设计原则

1. **图优先，不是文件夹优先**：文件夹按用途分组，链接按含义分组。一篇笔记只有一个家，但链向许多上下文。
2. **知识库优先记忆**：所有持久知识住在库内的主题笔记里；agent 私有的记忆索引只是**指向库位置的指针**，永远不是存储本体。
3. **渐进披露**：会话开始只注入轻量上下文；全文按需检索；整文件读取是最后手段。用**字节预算 + 硬上限**强制「会话成本与库体积无关」。
4. **agent 无关内核**：钩子脚本、子代理提示、命令定义、库约定都是纯 Markdown 与 TypeScript，无 SDK 依赖。只有宿主专属的自动记忆加载器与插件不可移植。

> 四条原则「违反其一需极好理由」。改动方案必须逐条对照。

## 5. 常驻上下文的硬上限

宿主对钩子的标准输出有**不可配置的字符上限**。超出后会话只拿到文件路径与前一小段预览——**而日志仍然记成功**。这是本系统最危险的静默失败。

- 预算字段即使被设得更大，脚本也会把它**夹到上限以内**（预留计量表空间）
- 走「指令文件」通道时预算可以更大，因为不受同一上限约束
- **预算不是压缩手段，是失控保护**：计量表是检测器，预算是紧急刹车

## 6. 扩展接缝与刻意敌视的改动

**鼓励扩展的位置**：库根清单字段、命令定义、子代理定义、笔记模板、查询视图、分类信号表、钩子脚本。

**刻意敌视的改动**（历史上都出过事故）：

| 改动 | 为什么敌视 |
|------|-----------|
| 把记忆存到库之外 | 破坏「知识库优先记忆」，且不可版本化 |
| 绕过库根清单 | 各层会各自推断版本与边界，静默不一致 |
| 在脚本里硬编码宿主事件名 | 破坏 agent 无关内核 |
| 按调用仓给笔记切分作用域 | 曾直接杀死最有价值的实测能力——值得要的答案恰恰来自**连接**不同项目 |
| 新增第二条读取路径 | 两处历史重新推导都放行了本该被策略扣留的笔记 |

## 7. 长期稳定保证（范围很窄）

**保证稳定**：库根清单的键、钩子脚本文件名、跨仓服务的启动脚本路径、用户内容目录布局。

**允许演进**：命令名、子代理内部实现、分类逻辑。

## 8. 两个存储、一个库

| 维度 | 主题笔记（`brain/`） | 记忆捕获（`memories/`） |
|------|---------------------|------------------------|
| 谁写 | 任意会话 | **只有跨仓服务**（库内会话被拒绝写入） |
| 形状 | 一篇可维护的文档 | 一条带声明受众与置信度的**不可变声明** |
| 可达范围 | 本库 | 由写入时声明的作用域决定 |
| 更正方式 | 直接改 | 用**取代**标记，不改正文 |
| 浏览方式 | 直接打开 | 专用查询视图（不要手工编辑） |
| 是否作为资源对外服务 | 是 | **永不作为普通笔记服务** |

## 9. 失败模式与可见性

| 失败 | 表现 | 怎么让它可见 |
|------|------|-------------|
| 索引名不一致 | 检索无结果 | 启动时校验五个调用方取值一致 |
| 注入超限 | 会话只拿到预览，日志说成功 | 计量表 + 端到端送达门禁 |
| 记忆作用域写错 | 该看到的看不到 / 不该看到的看到了 | 健康自检报告 servable 与 named-only 两类计数 |
| 钩子输出被截断 | 上下文静默缺一段 | 让模型逐字引用上下文的**最后一行**与**中段标记** |
