## 案例 001 · 课表截图排程（2026-10）

**场景**：用户提供课表截图（多张图，含一张校区平面图），要求排成可执行日程。

### 系统侧漏洞（流程缺陷）

| # | 漏洞 | 实际表现 |
|---|---|---|
| 1 | 图像不可直读，转写为单点失败 | 主模型拿不到像素，只能由子代理 OCR 一次，全部风险压在单次转写上 |
| 2 | 相似词无约束 | 乐学楼 / 勤学楼 / 敏学楼 / 博学楼只差一字，误读未拦截 |
| 3 | 一次性转写、无交叉校验 | 读一遍就用，周五 1-2 节、11-12 节两格直接漏读 |
| 4 | 缺置信度标注 | 军理教师姓名、单双周标记等模糊小字未标"低置信"，直接进方案 |
| 5 | 缺"先锚定再排程"闸门 | 未在排课前让用户确认楼名清单，错误一路传到排程阶段才被用户发现 |
| 6 | 校区平面图未被当作白名单 | 图 3 本可列出全部合法楼名，用来卡掉"教学楼702"这类非法值，但当时没用 |
| 7 | 错误跨阶段放大 | Phase 1 错一处 → Phase 2 精力分析、Phase 3 转场风险全部跟着错 |

### 应用侧隐患（用户实际使用中的风险）

| # | 隐患 | 说明 |
|---|---|---|
| 1 | 单/双周、特殊周极易漏课 | 编程实验与军理只单周、心理只双周、18-19 周国安课密集，记错周次就白跑 |
| 2 | 转场临界仍有 | 周四晚已降级为同楼，但 703→306（20min）、301→田径场（含更衣）仍是临界 |
| 3 | 周四"地狱日"无执行剧本 | 靠临场反应容易乱 |
| 4 | 空周认知缺失 | 第 1、17、20 周常规课全空（疑似缓冲/考试周），18-19 周突然密集，节奏会断 |
| 5 | 课表躺在聊天里不可执行 | 未进手机日历，课前不会提醒"去哪栋楼" |

### 对策映射（已固化为 v3 能力）

| 对策 | 内容 | 落到哪里 |
|---|---|---|
| A | 地图楼名白名单 + 转写校验 | fact-verifier 核心能力 1；`references/uncertainty-governance.md` §2 |
| B | 双代理独立读图 + diff | fact-verifier 核心能力 2；`references/uncertainty-governance.md` §3 |
| C | 置信度闸门 + 排程前确认 | fact-verifier 核心能力 3/4；主理人 SOP Phase 0.5 |
| D | 导出可执行日历（.ics/表格 + 课前提醒） | delivery-automator；`references/executable-delivery.md` |
| E | 单双周/特殊周自动化提醒 | delivery-automator 核心能力 3；`references/executable-delivery.md` §4 |
| F | 周四执行剧本 + 空周提示 | schedule-architect 核心能力 5/6；`references/execution-playbook.md` |

### 通用教训（适用于所有材料驱动的排程）

1. **枚举源就在材料里，但没人去找**——平面图、图例、表头、代码表都是白名单，先抽出来再读表。
2. **覆盖率比正确率更重要**——漏读的格子不会报错，只会安静地消失；逐格编号扫读是保证覆盖的唯一可靠方式。
3. **不确定必须可视化**——置信度不是内部状态，必须出现在给用户的输出里。
4. **闸门要前置**——在排程前让用户花 30 秒确认，比在排程后被用户揪出错误便宜十倍。
5. **交付才算完成**——没有进日历、没有提醒的日程，等于没做。
6. **降级一处不等于消除风险**——临界项要全量遍历，不处理最显眼的那个就收工。
