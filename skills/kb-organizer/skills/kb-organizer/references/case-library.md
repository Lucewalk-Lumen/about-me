# 场景案例库 — 知识库智能整理大师（knowledge-base-organizer）

> 用途：接到"整理知识库"类任务时先对照本库，复用已验证做法、规避已踩过的坑。
> 数据截至 2026-09-11。案例中涉及具体项目的条数、金额以权威库为准，未核实处标【待核：具体说明】。
> 案例 1、3 为真实业务场景的提炼（项目名、条数已做占位处理）；案例 2 为技能内演示场景，数字取自 SKILL.md 示例，非真实账。

---

## 案例 1｜项目资料库按主题分类重建（完整模式）

- **背景**：某市政污水 PPP 项目公司（临潼）的副总经理，项目资料库从建设期逐年累积，根目录 0 个文件夹，全部为散件，条数【待核：以 get_knowledge_list 实扫为准，初步目测数百条】。内容混杂：竣工验收资料、结算送审清单、合同与补充协议、政府函件与审批件、农民工保证金材料、监理例会纪要、造价定额与计价依据截图、公众号政策解读。使用中的具体痛点：要开股东会汇报结算口径时，反复用关键词搜索仍找不齐送审与审计两类文件，同一份合同扫描件与政府复函混在两处被重复引用。

- **做法**：
  1. **Phase 0 扫描定模式**：`search_knowledge_base` 取到 kb_id 后，用 `get_knowledge_list` 扫根目录，翻页上限 10 次（约 500 条）。判定结果：已有文件夹 0 个 → 走完整模式。同时记录 media_type 分布（该库以 1=PDF、6=公众号、7=Markdown 为主）。
  2. **Phase 1 内容画像**：用五组关键词做 `search(source="kb")` 语义搜索——"竣工验收 结算 审计"／"农民工 保证金 专用账户"／"PPP 合同 特许经营 补充协议"／"监理 例会 纪要"／"定额 清单 综合单价"，配合标题关键词聚类，确认内容主干是"建设期—结算期—运营期"三段。
  3. **Phase 2 出三个方案**：方案A 按项目阶段+专业（推荐）；方案B 按资料用途（对外函件／内部台账／合同／造价依据）；方案C 按时间年份。关键判断：**分类主维度选"项目阶段"而非"文件类型"**，并明确"同一维度下文件夹不超过 12 个"。用户选方案A。
  4. **Phase 3 建夹**：`create_folder` 建 10 个夹并记录回执 media_id（folder_ 前缀）作为后续 dst_folder_id：01-项目立项与批复、02-建设期竣工资料、03-结算送审与审计、04-合同与补充协议、05-政府函件与审批、06-农民工保证金、07-运营台账与化验数据、08-造价定额与计价依据、09-会议纪要、10-其他。
  5. **Phase 4 归类与批量移动**：按文件夹名动态生成关键词映射表（专有名词优先，如"特许经营""可行性缺口补助"），逐条匹配标题；先输出归类预览（各夹条数 + 未分类清单）等用户确认；再按目标文件夹分批 `move_knowledge`，每批 ≤10 条，逐批检查 `ret_code`。
  6. **Phase 5 验证**：复扫根目录，确认仅剩文件夹；输出整理前后对照表与失败项清单。

- **结果**：根目录由散件变为 10 个分类文件夹，散件归零（最终条数【待核】）。交付物为一份整理执行清单（含原路径记录）与一份整理前后对照表。实际效果：查结算送审口径由"关键词搜索多轮拼凑"改为"按 03 号夹直取"，股东会材料的资料准备环节不再逐份核对来源。

- **教训**：
  - **不要按 media_type 分**。第一轮曾尝试"PDF 一个夹、公众号一个夹"，结果是三个无检索价值的杂物堆——分类维度必须是"我要解决什么问题→去哪个夹找"，媒体类型只能写进方案说明当参考。
  - **合同与函件必须分夹**。同一份 PPP 合同的扫描件与政府对同一事项的复函如果同放一个夹，极易被误当作合同附件引用；两类的效力不同，混放是实质风险。
  - **移动前必须留原路径记录**。该库第一批移动后有 2 条返回 ret_code≠0，靠执行清单里的 media_id + 原所在位置才定位并补移；没有记录就只能全库重扫。
  - **归属不确定的宁先进"10-其他"**，不要强行塞进语义相近的夹子，否则后续检索会误命中。

## 案例 2｜根目录散件批量归类（整理模式，示例场景）

- **背景**：用户自建的"AI 工具箱"知识库，已有 8 个文件夹（01-教学备课与课件制作 至 08-办公效率与数据分析），但根目录历年累积了约 214 条散件（**示例数据，取自 SKILL.md 演示，非真实账**），用户指令是一句话："帮我把根目录清一下。"

- **做法**：
  1. **Phase 0 判模式**：散件 214 条 > 5 且已有文件夹 > 0 → 整理模式，跳过 Phase 2、Phase 3（不建新夹）。
  2. **Phase 1 降级画像**：整理模式下不做全量语义 search（每次 search 的消耗约等于扫 200 条标题），只对标题做关键词聚类，识别出教学备课 35%、AI 工具 30%、论文课题 18%、图片视频 12%、政策报告 5%。
  3. **Phase 4 反向生成规则**：从已有 8 个文件夹名反推关键词表，匹配优先级依次为专有名词（WorkBuddy、ima、Coze、扣子）> 功能词（备课/课件/教案）> 形式词（论文/课题/申报）。
  4. **预览与确认**：输出各夹条数统计，未分类仅 3 条，逐条请用户指定，用户直接回答"1 归 05、2 归 08、3 新建其他"。
  5. **移动与验证**：按目标夹分批移动（每批 ≤10 条），复扫根目录确认散件归零。

- **结果**：214 条散件归入既有 8 个文件夹，未分类 3 条按用户指定处置。用户未改动任何文件夹名，既有检索习惯不变。

- **教训**：
  - **整理模式绝不重建文件夹**。曾有一次在整理模式下按新方案另建一套夹子，用户历史分享出去的链接与记忆中的路径全部失效，等于把库搞乱。
  - **文件夹名含义模糊时先看内容再判断**。有一个夹名只写了缩写，打开夹内 3-5 条内容才确定是"课题申报"类；按名称猜会把论文类错配进去。
  - **品牌词优先级最高**。不加这条规则时，"AI 工具教程"与"教学备课"两类会互相抢条目——含"AI 助教"的教案会被吸进工具夹。
  - **未分类 ≤5 条时逐条问用户比建"其他"夹更耐用**；一旦"其他"超过 10 条，它就变成第二个散件堆。

## 案例 3｜多知识库体系梳理（跨库任务的边界处置）

- **背景**：用户同时有 3 个知识库（工作／学习／个人），工作库最乱，学习库次之，个人库基本整洁。用户原话是"都帮我理一理，统一一下格式"。

- **做法**：
  1. **先声明边界**：`move_knowledge` 要求 `src_knowledge_base_id` 与 `dst_knowledge_base_id` 为同一知识库 ID，**跨库移动不在技能能力范围内**。因此在动手前即向用户说明：本技能负责"单库内部分类与归位"，跨库合并需用户自行操作。
  2. **逐库单独走流程**：按"工作库 → 学习库 → 个人库"顺序，每库各自完成 Phase 0 扫描 → 出方案 → 等确认 → 建夹/归类 → 移动 → 验证，不并发推进。
  3. **个人库直接结束**：Phase 0 扫描发现根目录散件 ≤5 条、结构清晰，按边界规则告知"根目录已整洁，无需整理"，未做任何改动。
  4. **统一命名规范**：为三库约定同一套文件夹前缀写法"两位序号-主题"（如 01-、02-），并在第一个库执行时就锁定，后续库照搬。
  5. **跨库重复文件只列清单**：发现工作库与学习库有 4 组同名文件，因 API 不支持删除，仅输出清单（含两库的 media_id）交用户手工处理。

- **结果**：工作库、学习库各自形成结构；个人库未改动；跨库重复清单 4 组交用户手工处置。总耗时显著长于单库任务，主因是三次独立的确认往返。

- **教训**：
  - **一次只问一个库的确认**。曾把三个库的方案一次性摆给用户，用户无法判断哪个方案更适合自己的使用习惯，最后要求拆开重看。
  - **不要试图跨库"合并同类项"**。跨库移动会失败或产生异常归属，且会破坏原有的分享链接权限。
  - **命名规范必须一次说清并使用同一种写法**。第二次执行时出现过"01-教学"与"教学资料-01"两种写法并存，用户按名称排序时两批文件被拆散。
  - **整洁的库要敢于不动**。个人库扫描后直接判定"无需整理"是正确的，对整洁库强行重分类属于过度整理。

## 复用速查

| 你的情形 | 参照案例 | 关键动作 |
|---|---|---|
| 根目录 0 文件夹、散件数百条 | 案例 1 | 完整模式；按"用途/阶段"分，不按文件类型分 |
| 已有文件夹、根目录散件几十条 | 案例 2 | 整理模式；从已有夹名反推关键词，不建新夹 |
| 用户要求同时处理多个库 | 案例 3 | 先声明跨库边界；逐库串行；统一命名前缀 |
| 扫描后散件 ≤5 条 | 案例 3 个人库 | 直接判定"已整洁"，不做改动 |
