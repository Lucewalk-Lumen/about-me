# Karpathy LLM 知识库（LLM Wiki）
> **归属**：基础能力层（foundation）——知识库，挂主理人 lead 按需注入


一种用 LLM 搭建个人知识库的方法模式。

## 核心理念

不采用 RAG（每次查询时临时检索），而是让 LLM **增量构建并维护一个持久化的 wiki**——一组结构化、互相链接的 Markdown 文件。每新增一份资料，LLM 就通读它、提取关键信息，并融入现有 wiki：更新实体页、修订主题综述、标记相互矛盾之处、强化不断演化的综合结论。

**Wiki 是一个持续复利的持久产物。** 交叉引用已在其中，矛盾已被标记，综述反映了已读过的全部资料。每多一份资料、每多一个问题，它都更丰富。

你不需要亲手写 wiki——全部内容由 LLM 撰写与维护。你负责提供资料、探索方向和提出正确的问题。

## 架构（三层）

### 1. 原始资料（Raw Sources）
你精选的资料文档集合——文章、论文、图片、数据文件。它们是**不可变的**：LLM 只读取、绝不修改。这是唯一事实来源。

### 2. Wiki 本体
由 LLM 生成的 Markdown 文件目录——摘要页、实体页、概念页、对比页、总览、综述。这一层完全由 LLM 负责：创建页面、在资料到来时更新、维护交叉引用、保持全局一致。**你负责读；LLM 负责写。**

### 3. Schema（结构规范）
一份配置文档（即本技能），规定 wiki 的结构、约定与工作流。它与使用者共同演化。

## 操作

### 导入（Ingest）
用户放入一份新资料。LLM：
1. 通读资料并讨论要点
2. 在 wiki 中写一页摘要
3. 更新索引
4. 更新 wiki 中相关的实体页与概念页
5. 在日志中追加一条记录

一份资料可能牵动 10–15 个 wiki 页面。为保证质量，建议一次只导入一份资料。

### 查询（Query）

面向 wiki 提问。LLM 遵循「**检索 → 综合**」两阶段流程：

1. **检索**——先读 `index.md`（若有 `WIKI-SCHEMA.md` 也一并读），按相关性圈定候选页面；只读候选页（先读 frontmatter，仅高相关页读全文），带引用地综合出答案。
2. **综合与引用**——以 Markdown 报告 / 对比表 / 要点列表作答；每个论断都标注来源 `[[page]]`（若直接取自原始资料则标注 `[[raw/xxx]]`）。
3. **回存**——好的答案沉淀为新 wiki 页面（对比、分析、关联），而不是散落在聊天记录里。

#### 查询检索规范

查询阶段必须满足以下七个质量维度。这些是流程硬规则，不是可选项——它们让 LLM-Wiki 查询保持严谨，**同时**不重新引入逐查询 RAG。

1. **覆盖面**——检索面首先指向已编译的 `wiki/` 层（`index.md` + 实体/概念/主题页）。仅当用户明确要求查原始资料、或编译层无命中时，才转到 `raw/`（只读）。支持 Markdown / 纯文本 / CSV / JSON / 代码注释类资料；图片仅按题注索引，不做解析。默认查询当前 `wiki_root`；跨库查询须由用户提供第二个显式路径。两层都未命中时，明确答复「知识库未覆盖」并建议网络检索（`crawler` / `content-summary`）——绝不编造。

2. **准确与相关**——将查询关键词与页面 frontmatter（`title` / `type` / `tags` / `sources`）及摘要匹配。只读判定相关的页面；仅标题匹配而正文无关的页面标记「弱匹配」并降权、排除出结论。区分 LLM 推断与原始事实（依据专业伦理）。

3. **效率**——优先「编译时」而非「运行时」：用 `index.md` 与 frontmatter 做首轮粗筛，绝不重读整个 wiki。先读 frontmatter，仅高相关页读全文。大库分批处理（每轮 ≤8 页）并汇报进度。同一会话内复用已读页面，不重复读盘。

4. **灵活性**——支持多维度过滤：`type`（entity/concept/topic/comparison/source-summary）、时间窗口（`created`/`updated` 区间）、`source`（文件名）、`tags`。对近似拼写与中英混排查询启用模糊匹配（如「transformer」与「Transformer 架构」）。通过既有 `[[wiki link]]` / See Also 与领域同义词表（可在 `WIKI-SCHEMA.md` 中定义）扩展召回。

5. **排序与去重**——按相关性排序候选（标题/标签命中权重高于正文命中）；综合页/主题页优先于碎片页。多个页面指向同一概念时合并呈现，避免重复；多个来源互证同一事实时并列引用，而非重复叙述。

6. **边界处理**——空查询：向用户索要主题/维度，绝不整库倾倒。特殊字符/超长输入：截断或分片；超长查询拆为子问题，分别检索后合并。wiki 缺失/为空：如实说明并引导初始化（第 1 步）。无命中：答复「未覆盖」并给下一步建议，绝不编造。

7. **可解释性**——每个结论都标注 `[[page]]`（或 `[[raw/xxx]]`）。答案末尾列出命中页面**及命中的关键词/维度**，供用户核验。LLM 推断（非原文事实）标注〔推断〕。

### 体检（Lint，健康检查）
定期对 wiki 做健康检查，排查：
- 页面之间的相互矛盾
- 被更新资料取代的过时论断
- 无入链的孤儿页面
- 被反复提及却没有独立页面的重要概念
- 缺失的交叉引用
- 可通过网络搜索补齐的数据缺口

## 默认位置

Wiki 存放在**用户级**路径，任何工作区、任何会话都能访问：

```
~/.workbuddy/wiki-knowledge/
```

以上是默认值。LLM 应：
1. 只要用户提到自己的 wiki，**始终先检查 `~/.workbuddy/wiki-knowledge/`**，无论当前工作区是什么。
2. 若该目录存在且含 `WIKI-SCHEMA.md`，直接使用——无需再向用户索要路径。
3. 仅当用户明确想要一个独立 wiki 时，才询问自定义路径。

## 快速上手

当用户想创建 wiki 时，按以下步骤执行：

### 第 1 步：初始化结构
在 `~/.workbuddy/wiki-knowledge/`（或用户指定路径）创建：
```
wiki-knowledge/
├── raw/              # 不可变的原始资料
│   └── assets/       # 下载的图片
├── wiki/             # LLM 维护的 Markdown 文件
│   ├── index.md      # 内容目录
│   └── log.md        # 按时间排序的操作日志
└── WIKI-SCHEMA.md    # 结构规范与约定（与用户共同演化）
```

### 第 2 步：创建 index.md
全库目录——每页一条：链接、一句话摘要、元数据（日期、资料数）。按类别组织。每次导入后由 LLM 更新。

### 第 3 步：创建 log.md
只追加的时间线记录。每条格式：
```markdown
## [YYYY-MM-DD] operation_type | Title
Brief description of what was done.
```
使用统一前缀，保证可用 grep 解析：
```bash
grep "^## \[" log.md | tail -5
```

### 第 4 步：创建 WIKI-SCHEMA.md
一份配置文件，描述：
- 目录结构与约定
- 页面格式模板
- 交叉引用规则
- 领域专属分类
- 导入/查询/体检的工作流

与用户一起，针对其具体领域定制。

## 页面格式模板

```markdown
---
title: Page Title
type: entity | concept | source-summary | comparison | synthesis
created: YYYY-MM-DD
updated: YYYY-MM-DD
sources: [list of source filenames]
tags: [relevant tags]
---

# Page Title

Content here. Use [[wiki-links]] for cross-references.

## See Also
- [[related-page-1]]
- [[related-page-2]]
```

## 应用场景

| 领域 | 原始资料 | Wiki 页面 |
|------|---------|----------|
| **个人** | 日记、文章、播客笔记 | 目标、健康追踪、自我提升 |
| **科研** | 论文、文章、报告 | 实体、概念、演化的核心论点 |
| **读书** | 章节笔记 | 人物、主题、情节线索 |
| **企业** | IM 群聊、会议记录、文档 | 内部知识库 |
| **竞品分析** | 公司报告、新闻 | 竞品画像、对比 |
| **课程笔记** | 讲义、阅读材料 | 主题摘要、概念图 |

> **跨场景用法**：领域专家（case-writer / thesis-mentor / minutes-organizer / course-builder / grant-writer 等）在用户明确要求参考团队既往成果或本地知识库时，可经本技能执行「检索 → 综合」查询；无则跳过，不阻塞其主流程。

## 实用技巧

- 用 **Obsidian** 作为 wiki 查看器效果很好——图谱视图展示关联，Dataview 插件可查询 frontmatter 元数据
- **wiki 本质上就是一个 Markdown 文件的 git 仓库**——版本历史、分支与协作白送
- **Marp** 可基于 wiki 内容生成幻灯片
- **Web Clipper**（Obsidian 插件）把网页文章转成 Markdown，便于作为资料导入
- **图片下载到本地**以保证持久性——设定固定的附件目录

## 重要原则

1. **原始资料不可变**——绝不修改资料文档
2. **wiki 由 LLM 负责**——用户阅读，LLM 撰写与维护
3. **知识复利**——每次导入与查询都让 wiki 更丰富
4. **好答案要回存**——不要让有价值的分析消失在聊天里
5. **定期体检**——随 wiki 增长持续保持健康
