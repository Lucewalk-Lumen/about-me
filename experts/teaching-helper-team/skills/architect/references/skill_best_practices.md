# Skill 最佳实践指南（内嵌整理版）

> 来源：内部整理（参考通用 Skill 设计实践）。用于指导技能设计、审查和生成自定义 skill（平台无关）。

## 1. Skill 是什么

Skill 是一份清晰、严谨、可执行的指令文档，用来告诉 Agent：在什么场景下调用、需要哪些输入、遵循什么步骤、输出什么结果。它本质上是一份可运行 SOP：面向机器要结构化、无歧义、可执行；面向人类要可读、可维护、便于迭代。

## 2. 常见误区

- 把 Skill 当成普通说明书，缺少输入约束、边界条件和失败处理。
- 只记录一次性操作，没有抽象成稳定流程。
- 过度依赖 Agent 自己发挥，缺少关键约束。
- 忽略 `SKILL.md`、`scripts/`、`references/`、`assets/` 的职责分工。

## 3. 元数据要求

成熟 Skill 至少应表达：

```yaml
name: skill-name
version: 1.1.1
description: 用 1～2 句话说明 Skill 解决什么问题、服务哪些场景。
inputs:
  - name: input_path
    type: string
    required: true
outputs:
  - name: report_path
    type: string
constraints:
  - 不得直接修改生产数据库
labels:
  - domain:agent
  - risk:low
```

元数据目标：可发现、可组合、可治理。

## 4. 核心设计原则

### 简洁是关键

- 优先表达约束和关键路径。
- 明确“能做什么 / 不能做什么 / 先做什么 / 后做什么”。
- 复杂背景沉淀到 `references/`。

### 适当自由度

- 安全性、幂等性、资源消耗要强约束。
- 文案、可视化等创意部分可适度开放。
- 采用“必做步骤 + 可选增强”。

### 渐进式披露

- 主体先写 Happy Path。
- 高级用法、边界处理放后文或 `references/`。
- 降低首次使用门槛，避免信息过载。

## 5. 推荐目录结构

```text
skill-root/
  SKILL.md       # 主说明文档：元数据、流程、约束
  scripts/       # 可执行脚本
  references/    # 长文档、协议、调研报告
  assets/        # 图片、样例数据、静态 HTML
```

- `SKILL.md`：单一真相源，说明适用场景、输入输出、流程、注意事项、风险。
- `scripts/`：强绑定可执行脚本，参数必须在 `SKILL.md` 中说明。
- `references/`：长文档、协议、接口列表、调研报告。
- `assets/`：图片、样例数据、静态 HTML 等辅助资源。

## 6. 创建流程

1. 识别需求与边界：明确核心问题、目标用户、输入输出、允许访问的数据源、可写入位置和外部依赖。
2. 设计结构与元数据：确定目录、命名、输入输出、风险标签和约束。
3. 编写 `SKILL.md`：前半部分聚焦使用说明和流程，后半部分补充限制、反模式、FAQ。
4. 实现并绑定 `scripts/`：脚本入参与文档一致，避免隐式依赖某台机器。
5. 自测与反模式检查：检查危险默认值、隐式上下文、幂等性、失败处理。
6. 发布与持续迭代：评审文档、脚本、日志和监控；用版本号记录变更。

## 7. 反模式检查清单

- 输入/输出不清晰：缺少必填参数、默认值、输出路径或格式。
- 过度依赖隐式上下文：假设当前目录、环境变量、网络环境固定。
- 缺乏幂等与失败处理：重复执行产生重复副作用，无回滚方案。
- 日志与监控缺失：执行过程无关键日志。
- 文档与实现不一致：示例无法运行，脚本参数与说明不匹配。
- 安全与权限风险：默认生产写入、删除、覆盖、批量修改，未限制资源范围。

## 8. 验证与验收

- 功能验证：用不同规模、不同结构输入做多轮测试。
- 文档验证：让第一次接触的人按 `SKILL.md` 独立调用。
- 集成验证：挂接到实际 Agent 流程，检查入参拼装和输出消费。
- 回归验证：把历史问题场景沉淀为长期质量保障用例。

## 9. Agent制作助手落地规则

当用户上传或希望生成自定义 skill 时，必须检查：

1. 是否有清晰的 `name` 和 `description`。
2. 是否明确触发场景、输入、步骤、输出和边界。
3. 是否将复杂资料放入 `references/`，脚本放入 `scripts/`，静态资源放入 `assets/`。
4. 是否避免生产危险默认值和不可控副作用。
5. 是否提供最小可用示例和失败处理建议。
6. `SKILL.md` frontmatter `name` 是否与目录名一致。
