## 一、四个口径（引用时必须写明用哪一个）

| 口径 | 数值 | 说明 |
|---|---:|---|
| **类键数** | **62** | `warning-library.jsonl` 的**行数**。类键 = 消息原文 **+ 该行回显的变量名/文本片段** |
| **消息种类数** | **39** | 把回显片段替换为占位符后归并的结果 |
| 出现条数 | **219** | 全部 `n` 之和 |
| 涉及文件数 | **90** | 全部 `cases[]` 的并集（`.out` 份数） |

**「39」的可复现归并规则**（只有三条，其余一律不并）：

| 规则 | 命中前缀 | 并成 | 原类键 |
|---|---|---|---|
| R1 | `INPUT LINE EXCEEDED 90 CHARACTERS` | 1 种 | 13 类：W27–W36、W46、W52、W53 |
| R2 | `ALL CONTINUOUS LATENT VARIABLE COVARIANCES INVOLVING` | 1 种 | 10 类：W11、W12、W15、W16、W20、W21、W41、W42、W43、W55 |
| R3 | `THE LATENT VARIABLE COVARIANCE MATRIX (PSI) IN GROUP` | 1 种 | 3 类：W10、W17、W18 |

62 − 12 − 9 − 2 = **39**。

> ⚠ **不要用「更松的规则」。** 实测：若进一步剥掉「第二个句子起」并把 `WITHIN`/`BETWEEN` level 归一，会得到 **33**。
> 那是**过度归并** —— 它把 `IN THE MODEL COMMAND` 与 `IN THE MODEL POPULATION COMMAND`、
> `ON THE WITHIN LEVEL` 与 `ON THE BETWEEN LEVEL` 这些**语义有别、修法不同**的消息并成一条，
> 会把使用者引向错误的修改方向。**口径松紧直接改变结论，故规则必须写死。**

## 三、五条解读纪律

1. **不得把「警告」说成「错误」。** 官方语料 **555 份 `.out` 中 `*** FATAL ERROR` = 0 例**；
   90 份含警告的输出**全部正常运行结束**。警告 ≠ 运行失败。
2. **不得替 Mplus 补充它没说的话。** 只可陈述消息原文含义 + 官方 UG/FAQ 的对应说明；
   凡是「本次为何触发」的推断，一律标 **【推断待验证】**（P0-0a）。
3. **不得外推频次。** `n` / `文件` 是**这份官方语料**的实测，不是 Mplus 用户的总体发生率。
4. **不得只报消息不报位置。** 每条警告都要说清它出现在哪个段（`MODEL` / `OUTPUT` / `ANALYSIS`…），
   否则用户无从下手。
5. **不得编造未收录的消息。** 语料没有的警告类型就说「本库未收录此消息」，
   **不得凭印象补写一条看似合理的 Mplus 警告**（P0-0a 最高危形态）。

## 四、如何检索（禁止整库加载 · P0-5）

```bash
# 1) 按消息关键词找类键
grep -i "not positive definite" knowledge/facts/warning-library.jsonl

# 2) 取该类键的完整记录（含 text_full / n / n_cases / cases[] / commands{}）
#    → 只注入命中行，不读整个文件

# 3) 用 cases[] 里的 id 反查 cases.jsonl，再按需读该 id 的 facts 行
grep -n '"id": "ug-ch5-mcex5.18"' knowledge/facts/case-facts.jsonl
```

**输出给用户时**：先给消息原文，再给「属于本表哪一组 + 修法方向」，最后附来源
（`warning-library.jsonl` 的 `wclass_id` 与代表 `cases[]`）。**三步缺一不可。**
