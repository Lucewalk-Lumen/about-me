# 需求规格与任务规划

> 本团把「用户想法 → 可验收需求 → 可执行任务」的全过程纪律，供阶段 1–4（诊断 / 设计 / 实现）与主理人编排使用。

## 一、需求溯源五问（动笔前先答，答不出就先去问，不靠猜补齐）

| # | 要回答什么 | 判据（答成什么样算过） |
|---|---|---|
| 1 | **谁要的？** | 说出**发起人**与**受益用户**（可同一人，但不能是「大家」） |
| 2 | **解决什么已发生的问题？** | 举出**具体实例**（谁、什么场景、遇什么阻碍）；举不出实例 = 问题尚不存在 |
| 3 | **不做会怎样？** | 给出代价（量化优先：影响多少用户 / 时长 / 成本；不能量化则定性说明） |
| 4 | **怎么算做成？** | 给出**可验证判据**（指标 / 阈值 / 验收场景）；给不出则回第 3 问重估优先级 |
| 5 | **有没有更轻的解法？** | 先穷举再动手：**不做 / 少做 / 改配置 / 借现有能力 / 手工流程**，逐个问「它能达成第 4 问的判据吗」 |

第 5 问**最常被跳过、也最省钱**：穷举完仍只能靠开发实现，再进入实现。

## 二、伪需求甄别（命中 ≥2 个信号 → 先澄清再往下走）

| 信号 | 典型说法 | 甄别动作 |
|---|---|---|
| 方案先于问题 | 「用 XX 技术做 YY」「加个 AI」 | 回问：YY 解决前置五问里的哪一个？ |
| 说不清受益人 | 「对大家都有用」「提升体验」 | 补齐第 1、4 问；补不齐 → 降级为待定 |
| 竞品对标 | 「竞品有所以我们也要」 | 追问：我方用户是否与对方同构？有无数据支撑？ |
| 描述的是手段 | 「加个按钮」「导出 Excel」 | 翻译成**目标**后重述，再确认是否真要解决 |
| 单一来源无验证 | 「老板说要」「客户提的」 | 标注为**假设**并确认决策人，不当事实用 |
| 指标不可证伪 | 「提升满意度」 | 改成可测量判据，否则无法验收 |

## 三、价值判据（收益与回收期，五问通过后、动笔前）

| 项 | 算法 | 判据 |
|---|---|---|
| 年化收益 | 影响人数 × 频次 × 单次收益（或损失） | 三个因子都举不出 → 收益不可量化，回第 4 问重估 |
| 总成本 | 开发成本 + **长期维护成本** | 维护成本必须计入；只算开发成本视为低估 |
| 回收期 | 总成本 / 年化收益 | > 12 个月 → 须给战略理由，否则改走更轻解法 |

反模式：把「提升体验」「便于扩展」计入收益（不可量化）；只算一次性开发成本（漏维护成本）。

## 四、意图三段（先收敛到三句话）

- **Intent**：为什么要做这个变更
- **Scope**：变更范围（In scope / Out of scope 各列清楚）
- **Approach**：大致方向

## 五、模糊需求深挖（遇「合理 / 快速 / 稳定 / 安全 / 友好 / 智能 / 自动 / 尽快 / 可扩展」等词必须先转化）

| 深挖维度 | 需要回答 | 输出要求 |
|---|---|---|
| 判断标准 | 什么情况算满足？用什么指标？ | 给出可测试阈值 / 规则 / 示例 |
| 适用边界 | 哪些场景覆盖、哪些不覆盖？ | 写入 In / Out of scope |
| 正向案例 | 哪些输入应当通过？ | 至少 1 个（前置 → 操作 → 预期） |
| 反向案例 | 哪些输入应拒绝 / 报错 / 降级？ | 至少 1 个边界或失败场景 |
| 常见误区 | 容易被误解成什么？ | 明确不做什么，防范围扩散 |
| 验证证据 | 如何证明已满足？ | 测试 / 截图 / 响应 / 基准 / 用户验收 |

## 六、三件套（需求 / 设计 / 任务）

**Requirements**（行为契约，不是实现计划）：按新增 / 修改 / 移除三类，用 MUST/SHALL/SHOULD/MAY 强度词，每条至少一个场景（前置 → 操作 → 预期）。

**需求基线与变更条目**：用户确认后的 Requirements 冻结为 `00-需求/REQUIREMENTS.md`（目录契约见主理人工作目录契约）；中途变更**只追加** `00-需求/CHANGES.md` 变更条目——每条记「改什么 / 为什么 / 影响哪些阶段产物」，不改写基线原文；验收对「基线 + 变更条目」，防口头改需求与静默扩范围。

**Design**（技术方案）：技术思路 1–2 段 + 架构决策 + 文件变更清单。存在**多候选 / 高影响决策**时必须显式写「被否决的候选 + 反选理由 + 接受的代价 + 何时重估」；单一合理实现的低复杂度改动可跳过反选论证，避免「澄清过度」。

**Tasks**（实现清单）：按 Wave 分组，见 §九。

## 七、动工前规格验证

- [ ] 每条 Requirement 至少一个场景
- [ ] 每个场景可测试（有明确「前置 → 操作 → 预期」）
- [ ] 成功标准明确（「应当…」而非「可能…」）
- [ ] 变更范围聚焦（无无意识扩散）
- [ ] 模糊词已转化为判断标准 / 边界案例 / 验证证据

## 八、原子任务拆解（不得委派理解）

拆分或调度成员前，主理人必须先自行确认**目标、边界、验收口径、风险点**；成员只接收明确任务，不替主理人判断用户真实意图。同时识别：隐含依赖、风险点（复杂算法 / 第三方集成 / 性能瓶颈）、安全触发面（外部输入 / 权限 / 数据 / 文件 / 接口 / 后台操作 / 长任务 / 第三方回调）。

将复杂需求拆为 2–7 个原子任务（每 Wave 2–5 个）。每个任务必须：

- **单一职责**：只解决一个明确问题
- **可独立完成**：一个上下文窗口内可完成
- **可验证**：有明确完成标准
- **可回滚**：失败不影响其他任务
- **安全可验收**：涉及输入 / 权限 / 数据 / 文件 / 接口的任务必须含安全检查项
- **可委派**：目标 / 输入 / 输出 / 验收标准已明确；若仍需判断用户意图，须回 §一

**任务条目五要素（缺一不可）**：

1. **动作**：可执行的明确步骤，禁模糊指令
2. **出口校验**：本步完成的可判定标准（命令输出 / 断言 / 人工确认），禁「确认正常」式空话
3. **安全验证**：触发面逐项过，不涉及也写明原因，**禁止留空**
4. **回退**：失败路径明确，可逆 / 不可逆标注清楚，不可逆须标用户确认闸门
5. **checkpoint**：批量 / 长任务在每批完成后落进度与证据

**任务结构（XML，可选载体）**：`<task>` 含 `action / exit / verify / security / rollback / checkpoint / done` 七节点。

## 九、Wave 分组（按依赖）

```text
Wave 1（并行，无依赖）
├── Task 1.1 …  └── Task 1.2 …
Wave 2（依赖 Wave 1）
└── Task 2.1（依赖 1.1）…
```

**分组原则**：无依赖 → 同 Wave 可并行；有依赖 → 后续 Wave 必须串行；可能文件冲突 → 同 Wave 内串行或合并；涉及安全触发面 → 必须安排安全验证任务或写明验证方法。

**长任务专项**：若目标本身含长任务特性（批量 / 采集同步 / 大批量生成），按 `Init → Step → Poll → Cancel` 四段**串行**拆（建任务记录 → 分批幂等推进 → 查状态防僵尸 → 优雅取消），段内落 checkpoint。

## 十、批量子任务链式执行（不逐子等确认）

```text
☐ 子任务自主推进：N 个子任务按 Wave 依赖链自主完成，不逐子暂停等确认
☐ 仅关键闸门停顿：仅用户决策点（方案分歧 / 不可逆操作 / 安全相关）才停下询问
☐ 每 5 文件落 CHECKPOINT：进度 + 已验证证据，压缩上下文后仍可续做
☐ 批次阈值：≥3 文件未达 5 → 立即 checkpoint；单文件 >200 行 → 单独成批
☐ 单子任务失败不拖全链：失败项回滚后跳过或降级，其余继续，最后统一汇总
☐ 结果汇总统一呈现：全部完成后一次性输出各子任务完成状态 / 验证证据 / 遗留问题
```

**实测证据归档**：验证证据不得散落在对话中，须集中归档到报告的「实测证据」子区，按任务编号列出：命令 + 输出摘要 + 结论。

## 十一、上下文隔离与委派简报

执行单个任务时只加载必要上下文，**禁止**加载：无关模块内容、已完成无关任务细节、未决但无关的讨论、完整聊天记录。

```yaml
委派简报 = {
  task: 单一任务目标,
  background: 只保留与任务直接相关的背景,
  files: 允许读取或修改的文件范围,
  constraints: 技术 / 安全 / 输出限制,
  verify: 必须返回的验证证据,
  forbidden: 不得触碰的模块、不得扩展的范围
}
```

## 十二、执行与验证闭环

每个任务执行后：执行 → 自测 → 复核（对照目标完成度 / 格式 / 事实 / 一致性 / 边界 / 安全逐项）→ 记录 Task Summary → 通过则标记完成，失败则修复或回滚。

```text
## Task Summary: [任务名]
完成状态: [完成/部分完成/失败] | 修改文件: […] | 验证证据: [命令/输出/确认]
置信度: [高/中/低，低须说明原因] | 关键决策: […] | 偏差说明: […] | 遗留问题: […]
```

**批次聚合（防逐文件碎片化）**：同一 checkpoint 批次内的 Summary **聚合成一张表**输出（行 = 各文件 / 原子任务），随 `[CHECKPOINT]` 同输出；逐文件自测密度不降，仅记录方式聚合。

## 十三、委派全链路纪律

- **委派前（缺一不派）**：① 显式授权门槛（用户 / 规则 / 技能要求才用子代理）；② 有界且可独立验证才派；③ 简报三要素自足——目标 / 边界 / 验收口径写全，**禁假设子代理自带完整约定**；④ 复用检查先于新建；⑤ 独立子代理在单条消息内并行同发。
- **回收（防伪造、必消化）**：⑥ **禁编造或预测未完成子代理的结果**——完成通知永远不是主理人自己写的；⑦ 并行结果逐个检查，不抽样；⑧ 结果吸收进结论才算完成委派；⑨ 采纳的主张带证据或显式标为推断；⑩ 子代理报告由主理人消化后转述，不直达用户。
- **完成判定（防假完成）**：⑪ 四禁清单——测试失败 / 实现不完整 / 存在未解决错误 / 找不到依赖 → 禁标完成；⑫ 重复失败＝修根因，无回合上限；⑬ 预算或上下文耗尽 ≠ 完成；⑭ 终态归档需用户确认。
- **异常处置**：子会话失联 / 已断开 → 先打断 → 再发消息转向 → 归档需人确认。

## 十四、长任务执行可靠性

- **轮次上限仅约束单 Wave**，不跨 Wave 累计；大任务应 Wave 拆分 + 跨会话 `handoff.md` 续做；已验证 Wave 产出物不回退清零。
- **周期性检查点**：每完成一个 Wave 或累计 5 个原子任务，落检查点：`已完成项(带证据) + 相关文件 + 未完成项(下一步) + 阻塞项`——上下文压缩 / 崩溃后无损续做。
- **可靠交付物四要素**：① 已完成清单（每项带证据）② 未验证项 / 已知限制（不得隐藏）③ 部分失败明细（批次成败 / 可续做 / 失败原因）④ 下一步（动作与输入）。
- **观察与调度纪律**：完成条件须覆盖**每一个终态**（成功 / 失败 / 取消 / 超时）——「若此刻崩溃，我的条件会触发吗？不会就放宽」；轮询间隔按状态变化速度取（远程 ≥30s，本地 0.5–1s）；缺失的记录**不证明**「未发生」→ 回查本体状态。
- **无断点执行协议**：长任务只在**三类**情况停下等用户——① 破坏性 / 安全 / 不可回滚动作；② 方案歧义且**无已验证推荐项**；③ 必须由用户提供的输入。检查点、进度汇报、阶段切换、收尾**一律只落盘不请求确认**。**不停顿 ≠ 免门禁**：安全闸门、不可逆确认、未验证项披露照常执行。

## 十五、失败回退（需求与拆解阶段卡住时）

| 卡点 | 回退目标 | 最大重试 | 升级路径 |
|---|---|---|---|
| 意图过模糊 | 列 2–3 种理解请用户选 | 2 | 输出「需求澄清问卷」，待补充 |
| 模糊词无法转化 | 列 2–3 个互斥解释请用户选 | 2 | 同上 |
| Requirement 过宽泛 | 拆为多个子 Requirement 各对一个场景 | 2 | 输出骨架标「待细化」 |
| 方案与现有架构冲突 | 输出冲突点 + 备选方案 | 1 | 移交架构决策记录 |
| 任务依赖过复杂 / 循环依赖 | 识别并合并为单任务，或按维度分组 | 2 | 输出依赖图，建议拆分 |

## 十六、落地用法

- **阶段 0（立项确认）**：五问 + 伪需求甄别收敛为需求复述回执；确认后 Requirements 冻结为基线（§六）；口径未定不建 run。
- **阶段 1（诊断）**：五问 + 伪需求甄别 + 价值判据逐条过；答不出的项写进诊断报告的「待澄清」字段，不默认补全。
- **阶段 2（设计）**：意图三段 + 三件套成形；高影响决策留反选论证；任务清单按 §八–九 拆解。
- **阶段 3–4（实现）**：原子任务五要素 + Wave 分组成形；批量子任务走链式执行（§十）；主理人按 §十三 委派。
- **教学场景**：判据须叠加学术诚信（无编造数据、出处可核验）；企业场景叠加权限隔离与审计门禁。
