# 五维质量评估标准（资产接入 WorkBuddy 体验）

> 目的：从**构成完整性 / 任务完成度 / 指令遵从性 / 事实辨别性 / 规则遵从性**五个维度，检测一个专家资产（技能/专家/专家团）接入 WorkBuddy 后的真实体验。检测不通过时，对文件中信息做**精修调整**并接入 WorkBuddy 调试，而非仅报错。
> 主域：本团主域为 WorkBuddy 包开发；维度 D 的合规硬指标以官方规范为准。
> 基于本专家团 `workbuddy-expert-studio-flow-9stage.md` 阶段 1/阶段 5 的五维推演与一轮实测沉淀的评分锚点、严重度门控。

---

## 1. 五维定义与判据

每个维度给 **1–10 分 + 至少两条直接证据**。先逐维评分，再算平均分（保留一位小数）。证据须可溯源，结论与评分均须有出处支撑。

### 维度 A · 任务完成度（Task Completion）
资产能否**完整完成其声明核心任务**，无断点、无缺失产物。
| 判据 | 通过信号 | 不通过信号 |
|------|----------|------------|
| 核心任务声明清晰 | description / displayDescription 一句话说清做什么、为谁做 | 模糊、同质化、无边界 |
| 工作流完整 | 从识别→执行→交付无断点；有固定输出模板与验收标准 | 流程中断、缺产物、无验收条件 |
| 产物可交付 | 关键产物（报告/包/代码）有模板且可执行 | 只有概念、无落地产物 |

### 维度 B · 指令遵从性（Instruction Compliance）
响应用户指令是否**准确、一致、可复现**。
| 判据 | 通过信号 | 不通过信号 |
|------|----------|------------|
| 触发描述质量 | 四要素完整（场景/触发词/能力/边界），含正例与 near-miss | 触发词缺、误触发高 |
| 声明一致性 | description / displayDescription / 正文 / quickPrompts 互相一致 | 自相矛盾、口径漂移 |
| 指令稳定 | 同指令多次产出结构一致 | 随机跳步、擅自改范围 |
| 场景路由可执行 | 场景表六列完整、三场景齐备、附加门禁关键词有判据落点（排除自引用）、quickPrompts 覆盖三场景回退 | 路由表缺失 / 空承诺 / 自引用无落点 / 回退不可用 |

> 维度 B 内置**场景化合规检查**（`quality_eval.py` → `check_scenario_routing`）：场景路由表从文档承诺变脚本可验证；附加门禁关键词的判据落点见 `workbuddy-expert-studio-pkg-ops.md`「一·补 场景附加门禁」。

### 维度 C · 事实辨别性（Fact Discrimination）
输出事实是否**准确、可靠、可核验**。
| 判据 | 通过信号 | 不通过信号 |
|------|----------|------------|
| 来源可锚定 | 真实材料标注来源；转引附出处；不确定项标「待验证」 | 伪造来源、无出处断言 |
| 量化审慎 | 统计数据/样本/p 值等有依据，不编造 | 编造数字、夸大结论 |
| 证据标注 | 区分已验证/建议/待确认；推测不与根因混淆 | 把推断当事实陈述 |

### 维度 D · 规则遵从性（Rule Compliance）
是否遵守**内部规则与平台行为规范**。
| 判据 | 通过信号 | 不通过信号 |
|------|----------|------------|
| 合规硬指标 | plugin.json 合规硬指标全过（清单见知识库第 5 节） | 40-50字/3标签/一致性任一破 |
| 协作铁律 | 专家团含 TeamCreate-only / 不代写 / 中转 / 成员结论为准 | 缺失铁律或主理人代写 |
| 安全红线 | 无硬编码密钥、无混淆执行、无静默删除、无路径穿越 | 命中任一条安全红线 |
| 视觉纪律 | 无 emoji 图标、无 Indigo→Pink 渐变+发光+毛玻璃 AI 模板味 | 命中 P0 视觉红线 |

### 维度 E · 构成完整性（Composition Completeness）
包是否**把 Agent 构成六要素都落地了**（非空壳），对应 `workbuddy-expert-studio-harness.md` 构成模型。
| 判据 | 通过信号 | 不通过信号 |
|------|----------|------------|
| 身份与边界 | 有 plugin.json / SKILL.md 的名称与角色声明 | 无身份声明 |
| 工具与能力 | 有 skills/ 或 scripts/ 承载能力 | 只有说明、无能力落点 |
| 记忆与上下文 | 有 references/ 或 knowledge/ | 无知识沉淀 |
| 编排与循环 | 专家团有主理人文件 / 技能有流程 | 无编排定义 |
| 输出契约 | 有固定输出模板与交付物落点 | 无输出约定 |
| 门禁与演化 | 有门禁脚本或 CHANGELOG | 无门禁、无演进记录 |

> 与 `scripts/gates.py`（结构层硬门禁）互补：门禁判「有没有」，本维度判「落得实不实」。

## 2. 评分锚点与门控

评分锚点（1–3 阻断 / 4–6 需改 / 7–8 可用 / 9–10 成熟），收敛到五维：
- **1–3**：阻断。核心流程不可执行 / 存在安全红线 / 缺失必要产物。
- **4–6**：需修改。主体存在，但有断点、不稳定或重要证据缺失。
- **7–8**：可用但需优化。主要流程可执行、无阻断，仍有非关键缺口。
- **9–10**：成熟。流程完整、边界明确、证据充分、对异常有可靠处理。

**门控（GATE）规则**
- 五维均 ≥ 8 且平均分 ≥ 8.0 → ✅ **可接入（PASS）**
- 任一维 ≤ 3 或平均分 < 6.0 → 🔴 **阻断（FAIL）**，必须精修后复测
- 其余 → 🟡 **需修改（WARN）**，给出精修清单后择机接入

严重度标记：🔴 严重（必须修）/ 🟡 建议（应修）/ 🟢 可选（可延后）。

---

## 3. 不通过时的精修流程（接入调试闭环）

检测 🔴/🟡 时，不简单报错，而是进入**精修—复测**闭环：
1. `quality_eval.py` 输出逐维评分 + 证据 + 精修清单（文件:行号:建议）。
2. 主理人或对应成员按清单对文件做**最小侵入精修**（改内容、不动结构）。
3. 重新运行 `quality_eval.py` 与 `verify.py` 门禁，确认五维均达标。
4. 接入 WorkBuddy 调试：在测试环境加载资产，用真实用户口吻跑 2–3 个场景（含 1 条 near-miss），记录是否真会触发、产物是否达标。
5. 复测通过 → 落盘交付；仍有 🔴 → 回到步骤 2。

> 反模式警示：不得为「让扫描器通过」而放宽判据（修扫描器而非内容）。判据本身若过时，应先经 `sync_standards.py` 复核官方标准，再改判据。

---

## 4. 与现有门禁的关系

`quality_eval.py` 是**体验层**门禁（资产接入后好不好用）；`verify.py` + `scripts/gates.py` 是**结构层**门禁（包是否合规）。两者都必须在阶段 5/阶段 7 跑通（exit 0）才放行。
