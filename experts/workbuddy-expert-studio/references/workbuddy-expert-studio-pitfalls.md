# 包开发坑位库

> 本团开发 WorkBuddy 包时的坑位库，按 Agent 构成模型（`workbuddy-expert-studio-harness.md`）与九阶段重排，供阶段 1 诊断与阶段 5 审计对表。
> **适用域**：Agent 构成形态无关，§二 2.1「构成坑」对任何 Agent 目标（WorkBuddy 包 / 独立应用）**通用**；§二 2.3「包工程坑」为 WorkBuddy 包制品特有。

## 一、方法论 9 坑（诊断 / 全程先扫）

| # | 坑 | 解法 |
|---|---|---|
| K1 | 把长提示词当专家 | 提示越长效越脆；拆成职责边界 / 工具 / 记忆等可独立验证的部件 |
| K2 | 职责无边界 | 先写「边界卡」：能做什么、不能做什么、什么必须停 |
| K3 | 记忆一股脑塞上下文 | 三分法分流：工作记忆 / 长期记忆 / 画像，勿混用 |
| K4 | 无灰度直接全量 | 专家有随机性，无回归集上线等于盲飞；必须灰度 + 回滚 |
| K5 | 画像只增不删 | 错误画像持续污染对话；须有置信度、过期与更正机制 |
| K6 | 外源内容只做「部分吸收」 | 抓取 / 借鉴 / 安装时先立应吸收清单 → 逐条映射落点 → 未映射项显式列出 → 吸收后回查（见 `workbuddy-expert-studio-reasoning.md` §十一 A）；否则遗漏 → 返工 |
| K7 | 收到用户反馈不查证 | 先查证再动作，三向裁决（用户对→采纳+证据；我对→举证；都不对→澄清）；禁盲从、禁跳过（见 `workbuddy-expert-studio-reasoning.md` §十二） |
| K8 | 吸收了无关内容 | 吸收前过准入三问（主域相关 / 任务相关 / 写得出落点）；登记「来源 + 为什么吸收 + 落点」；无关内容显式丢弃留痕；登记外新增 = 违规吸收（见 `workbuddy-expert-studio-reasoning.md` §十一 B） |
| K9 | 引用了知识库 / 资产但没建立连接 | 引用了资产须逐条核实连接（指向存在 / 口径一致 / 锚点新鲜 / 编排路由）；本团实测三断连：基线键名 ≠ 检测器键名（永远假绿）、枚举全名 vs 数字（永远假红）、哈希锚漂移（示例，已脱敏） |
| K10 | Markdown 代码块内用 `##` 展示模板，被误识别为文档自身章节 | 输出契约等模板在代码块内展示时，章节标题用 `### N.`（三级）或纯文本编号，禁止 `##`（二级）；否则渲染器把它当文档章节，污染目录、误导门禁章节统计——本团发布前复核实锤（示例，已脱敏） |
| K11 | 版本号升级只改 plugin.json，漏改脚本内嵌版本串 | 版本号五处一致：plugin.json / SKILL.md×N / contract.yaml / CHANGELOG / **脚本内嵌版本串（user-agent 等）**；verify.py 的 embedded_version_scan 会抓，升级前全局 grep 旧版本号（示例：web-crawler 脚本 user-agent 漂移，已脱敏） |
| K12 | CHANGELOG 把多版本的改动混在一个版本标题下 | 每个版本标题只写该版本的改动：初版（x.0.0）只写智能体功能本身，后续版（x.0.1+）写修复与优化；合并版本时把被取代版本的条目并入目标版本，历史版本条目不跨版本重复 |
| K13 | 把「排版空格」误当「字段尾随空格」改数据 | 显示名「英文后要有空格」指**中英文之间的排版空格**（如「WorkBuddy 专家开发工坊」），不是字段值尾随空格；改动前先与用户确认是排版规范还是数据规范，避免改坏字段值后整批回退（本团发布前误判实例，已脱敏） |

## 二、坑位（阶段 3–4 实现 / 阶段 5 审计）

### 2.1 构成坑（形态无关：按 Agent 六要素组织）

| 构成要素 | 坑（速览） | 解法 |
|---|---|---|
| 身份与边界 | 职责无边界 / 单 agent 过载 / 无分层 | 边界卡；职责下沉为子技能；主文件分片 |
| 工具与能力 | 首轮不选工具即编造 / 工具过度选择 / 无工具白名单 | 首轮强制选工具；调用预算上限 + force-summary；allow/block list |
| 记忆与上下文 | 无界增长 / 把检索当记忆 / 滑窗失忆 | 三层压缩（占位→摘要→自压缩）；记忆分层；锚定窗口 |
| 编排与循环 | 死循环 / 依赖调用被强并行 / 部分失败混乱 | 终端态保证；依赖图调度；失败策略显式 |
| 输出契约 | 结构化文件先写后检 / 错误被吞 | 内存构造→解析预检→写盘→读回再验；错误上抛不吞 |
| 门禁与演化 | 门禁不会判红 / 教训只停在口头 | 绿红双证自检；踩坑固化为 Linter / 断言 |

### 2.2 横切关注点（贯穿六要素）

| 关注点 | 坑（速览） | 解法 |
|---|---|---|
| LLM 集成 | 无熔断 / 单模型依赖 / 配置冻结 / 推理模型参数不兼容 | 熔断 + 退避重试；模型池 + 连通性探测；动态配置 |
| 状态 | 恢复历史缺工具轨迹 → 请求报错 / 卡 running | 恢复时补配对；终端态保证；并发互斥锁 |
| 运维 | 定时任务碰撞 / 流式断连 / 启动竞态 / 容器 libc | 并发锁；终止事件保证；非阻塞容错启动 |

### 2.3 包工程坑（WorkBuddy 包制品特有）

| 类 | 坑（速览） | 解法 |
|---|---|---|
| 结构 | 主文件过大 / 单体 SKILL 过长 / 无路由表 | 主文件分片 + 顶部路由表；能力下沉为子技能 |
| 代码质量 | 死函数 / 外部格式漂移 / 正则误匹配 | 死码检测；真数据测试（非照文档）；上下文锚定 |
| 脚本安全 | ReDoS / 路径穿越 | 正则锚定 + 输入限长；穿越诱饵实测 |
| 选型 | 过度工程 / 框架锁定 / 运行期依赖 | 能不用框架就不用；核心逻辑保留可抽出 |

## 三、循环两不变量（阶段 5 审计判据）

- **进度通道**：长任务必须有进度事件，否则用户误判为死机。
- **终端态保证**：任何执行路径都必须走到 done / failed，**禁止永久 running**。

## 四、落地用法

- **阶段 1（诊断）**：按类逐条 grep 风险信号，命中即记一笔待审；先判目标落在六要素哪一块，再定位到 2.1 / 2.2 / 2.3。
- **阶段 5（审计）**：逐类对表；静态扫描命中连上下文甄别，假红假绿同等对待。
- **阶段 3–4（实现）**：把可代码化的坑写成门禁脚本（见包根 `scripts/`），不写成口头约定。
