# 成员接口契约规范（多智能体协同）

> 本团成员间「产物如何交接、信息如何流转、冲突如何裁决」的统一规范，供阶段 1–9 全程对照。
> 定位：解决「模块间接口不统一导致无法衔接」的根因——让每个成员的产出都能被下一个成员**按编号准确消费**，不再靠主理人经验中转。
> 与 `workbuddy-expert-studio-flow-9stage.md` 的关系：flow-9stage 规定「做什么」（九阶段动作），本文规定「怎么交接」（产物的形状与流转协议）。

---

## 一、三条根因与对策（本规范要解决的问题）

| 断点 | 现象 | 对策（本文章节） |
|---|---|---|
| 输出模板字段不统一 | 各成员产出字段命名与颗粒度各异，下游无法判断「没做」还是「漏传」 | §二 统一输出契约 |
| 缺少交接握手协议 | 只规定读写哪个目录，没规定下游消费上游哪些字段 | §三 消费输入声明 + §四 统一回传握手 |
| 冲突裁决无记录 | 成员产出矛盾时凭主理人经验拍板，决策不可追溯 | §五 冲突裁决与决策记录 |

---

## 二、统一输出契约（结构化产出固定章节编号）

每位成员的产出文档**必须用固定章节编号 + 必填字段**，章节编号一经定义不得增删改序。下游成员按编号消费，缺章即视为「该成员未完成」，由主理人退回。

| 成员 | 产出文档 | 固定章节（编号 + 名称） |
|---|---|---|
| 沈证（诊断） | `01-诊断/诊断报告.md` | 1 根因结论 / 2 证据三行 / 3 三档标注 / 4 本次局限 / 5 流程分支判定 |
| 高构（设计） | `02-设计/设计蓝图.md` | 1 包骨架 / 2 文件清单 / 3 成员六要素 / 4 协作拓扑 / 5 P0 红线 / 6 自引用扫描 / 7 流程分支 |
| 柯码（实现） | `03-源码/实现记录.md` | 1 主文件长度与分片 / 2 门禁脚本清单 / 3 负向对照证据 / 4 伪造替身清理 / 5 能力边界数字 |
| 严证（审计） | `05-审计/体检报告.md` | 1 建议结论 / 2 高中低 finding / 3 脚本复跑读数 / 4 未处理项 |
| 包洁（打包） | `06-打包/打包记录.md` | 1 输出路径与条目数 / 2 顶层前缀唯一性 / 3 沙箱校验 / 4 指纹比对 / 5 备份与重注册 / 6 发布与回滚 |
| 史衡（验收） | `07-放行/验收清单.md` 等 | 1 验收清单 / 2 版本四处一致 / 3 遗留项与局限 / 4 蒸馏资产 |

**标题层级纪律**：产出文档内的章节用**三级标题（`### N.`）**，与 MD 正文的二级章节标题（`##`）区分；若在 Markdown 代码块内展示模板，禁止用 `##`（会被渲染器误识别为文档自身的章节标题，造成标题污染，见 `workbuddy-expert-studio-pitfalls.md` K10）。

---

## 三、消费输入声明（每个成员显式声明读上游哪些字段）

每位成员在其 Agent MD 中必须有「消费输入」章节，用表格显式声明：

| 必填列 | 说明 |
|---|---|
| 来源 | 读哪个目录 / 哪份产物（相对 run 目录路径） |
| 读取内容 | 读该产物的**哪些章节 / 哪些字段**（引用 §二 的章节编号） |
| 用途 | 读来做什��（决定什么判据 / 落地什么产物） |
| 不读 | 显式排除的下游产物（防「参考了不该参考的结论」） |

**铁律**：禁止「读全部产物」这类模糊表述；必须落到具体产物 + 具体章节编号。成员只能读自己阶段之前的上游产物，禁止读下游产物（防循环依赖与「结论先行倒推」）。

---

## 四、统一回传握手协议（成员 → 主理人，固定五项）

每位成员完成产出后，回传主理人的内容**固定五项，顺序不可变**：

1. **产出文件路径**：相对 run 目录的路径（可多个）。
2. **一句话结论**：本阶段结论压缩成一句话。
3. **必填字段齐全性自检**：对照 §二 的章节编号逐项 ✓/✗。
4. **给下游成员的显式提示**：下游成员**必读哪些章节**（引用章节编号），作为下游「消费输入」的直接来源。
5. **建议结论**（仅供主理人裁决）：可进入下一阶段 / 待修复 / 待回炉。

**铁律**：成员只出「建议结论」，**最终放行决定权归主理人**，成员不得自行宣告放行；回传只传路径与要点，不传全文（状态写文件，不塞上下文）。

---

## 五、冲突裁决与决策记录（主理人职责）

1. 多成员产出相互矛盾时，主理人必须**显式裁决**（选哪个、为什么），不得和稀泥，也不得凭对话记忆拍板。
2. 裁决结果写进最终交付报告的「**决策与权衡**」章节：被选方案 + 被否决方案 + 否决理由 + 适用前提。
3. 技术选型类判断须给出**至少一个被否决的备选方案及理由**。
4. 裁决依据优先级：官方标准快照（`knowledge/`）> 方法文献（`references/`）> 成员建议结论。

---

## 六、编排规范（预设 Workflow + 直调路由）

主理人按「先判入口，再选 Workflow」编排，避免「轻量咨询也走全程」的浪费：

| Workflow | 触发 | 编排 |
|---|---|---|
| A 全量新建（默认） | 从 0 到 1 做包 | 阶段 0→1→2→3–4→5→6→7–9 串行 |
| B 审计已有包 | 看包 / 被驳回 / 体检 | 阶段 0→1→5→汇编 |
| C 重打包/改名 | 重打包 / 换版 / 改名 | 阶段 0→6→7–9 |
| D 轻量咨询（直调） | 只问某一单点 | 走直调路由表，不调全团队 |

**直调路由表**：只问诊断→沈证；只问结构→高构；只问分片/门禁→柯码；只问审计→严证；只问打包→包洁；只问验收/版本→史衡。综合/跨阶段→Workflow A。

---

## 七、落地用法

- **阶段 2（设计）**：高构按本规范为每个成员定义「消费输入 + 输出契约章节编号」，写进成员六要素。
- **阶段 3–4（实现）**：柯码落源码时，成员 MD 的「消费输入 / 结构化输出契约 / 回传要求」三章必须与本规范一致。
- **阶段 5（审计）**：严证对表——成员产出是否缺固定章节、回传是否齐五项、消费输入是否落到章节编号；缺一项记 P1。
- **全程**：主理人调度时把本规范作为交接判据；成员产出与本规范冲突，以本规范为准，不得自行放宽。
