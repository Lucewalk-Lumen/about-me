# Agent 构成模型与 Harness 纪律

> 本团对「一个 Agent 由什么构成」的通用底座，以及 WorkBuddy 主域约束与 Harness 工程纪律，供阶段 2 结构设计与阶段 4 质量校验使用。
> **主域声明（重要）**：本团主域是 **WorkBuddy 包开发**（技能 / 专家 / 专家团）。下文构成模型是**内部通用底座**，只用于保证「不漏块」；**判对错一律以 WorkBuddy 官方规范为准**——通用内容不得盖过 WorkBuddy 特性，也不得据此把本团产出泛化成「通用 Agent 开发」。

## 一、WorkBuddy 主域与特有约束（通用内容覆盖不到的部分）

| 约束 | 内容 |
|---|---|
| 包标识 | `name` == `plugin` == 顶层目录名 |
| 展示描述 | `displayDescription.zh` 40–50 CJK 字（非 `len()`） |
| 分类 | `categoryId` ∈ 官方 15 类枚举 |
| 团队字段 | `teamInfo.leadAgent == members[0] == agentName`；`members` 字段仅 id/name/profession/avatar/role |
| 触发 | `tags` = 3；`quickPrompts` = 3；`defaultInitPrompt == quickPrompts[0]` |
| 指令注入上限 | 平台约 2 万字符，超出静默截断（官方校验不查此项）；主文件超 1.8 万即分片 |
| 平台能力 | browser-skill 为平台内建，直接可用、不引第三方 |
| 交付形态 | 专家 / 专家团 / 技能三类；本团为 team 型 |

这些是 WorkBuddy **特有**、通用 Agent 内容没有的；本团一切产出**先满足它们**，再谈通用纪律。

## 二、Agent 构成模型（构成六要素 · 通用底座：用于不漏块）

> 定位：这是**心智模型**，帮你检查有没有漏掉一块；**不是验收标准**。DoD 以 §一 的 WorkBuddy 约束与 §三/§四 的门禁为准。

| # | 构成要素 | 回答的问题 | WorkBuddy 包落点 |
|---|---|---|---|
| 1 | **身份与边界** | 我是谁 / 能做什么 / 什么必须停 | `plugin.json`（name / profession / displayName）、`agents/*.md` 角色定义 |
| 2 | **工具与能力** | 靠什么完成工作 | `skills/*`、`scripts/*`、平台能力（browser-skill） |
| 3 | **记忆与上下文** | 记住什么、当前带什么进上下文 | `references/`、`knowledge/`、工作区文件、`handoff.md` |
| 4 | **编排与循环** | 谁调度、怎么拆解与收敛 | 主理人 SOP、`teamInfo`、Wave 编排 |
| 5 | **输出契约** | 对外交付什么、什么格式 | 结构化输出模板、交付物落点、回传要求 |
| 6 | **门禁与演化** | 什么算通过、教训怎么固化 | `scripts/verify.py` 等门禁、`CHANGELOG`、Linter / 断言 |

**用法**：设计时按**构成六要素**逐块对照缺哪补哪；审计时逐块查有没有「空壳」（有定义无落点 / 有落点无门禁）。构成六要素的落地检查见 `quality_eval.py` 维度 E「构成完整性」。
> **防混淆**：另有一套**结构六要素**（角色定义 / 擅长领域 / 分析框架 / 数据获取 / 结构化输出 / 回传要求，见 `workbuddy-expert-studio-flow-9stage.md` 阶段 2），约束的是**成员文档的形状**，由 `scripts/gates.py` 硬校验。两套「六要素」同名不同义，勿混用。

## 三、Harness 四大铁律（阶段 2 结构设计硬约束）

1. **上下文越少越好**——稀缺资源，像 Code Review 一样精挑。
2. **专才 Agent 永远赢过通才**——Agent 昂贵、Skill 廉价；**Agent 数默认 ≤3**，超出的下沉为 Skill；仅高并行 / 独立子任务可放宽到 3–5，且每个 Agent 须独立论证价值。
3. **状态要写文件，不要塞上下文**——Workspace 是可回放 / 审计 / 续传的真相之源。（呼应本团「消息只传路径与要点、不传全文」）
4. **能写成 Linter 的约束，别写成文档**——自然语言可被创造性解读，代码不能；**硬红线少而精**，只有「碰了必须停」的动作才设，且每条必须可代码化强制。

**边界说明**：「Agent ≤3」约束的是**单次运行时的编排 Agent 数**（一个应用内的 Orchestrator + Specialist），不是产品化专家团的成员编制。本团作为可上架产品，成员名单由九阶段职责的正交性决定（7 名 = 1 主理人 + 6 阶段专职），且**按需调度**，任一时刻并行执行的成员仍控制在少量，故不冲突。

## 四、Harness 六支柱（阶段 2 自检清单）

① Identity 身份（角色与权限边界）② Orchestration 编排（拆解 / 调度 / 收敛）③ Context 上下文（精挑压缩）④ Gate 门禁（生成与评估分离、硬拦截）⑤ Recovery 恢复（状态机 + 断点续接）⑥ Evolution 进化（踩坑本 → Linter 化）。
**三层归位**：身份层（谁 / 权限）→ 执行层（Context + Gate + Recovery，保证单次可靠）→ 进化层（把一次性教训沉淀成永久约束）。六支柱是构成模型的「约束切面」，二者看同一对象。

## 五、防编造三层（阶段 1 / 3 / 5）

- **A 阻断（Blocking）**：闭世界工具集收敛 + 强制首轮选工具 + 调用预算收紧。
- **B 告知（Informing）**：向用户显式声明「未知 / 置信度 / 来源」，不把推测当事实。
- **C 约束（Constraining）**：固定工具集 + 输出 schema 约束 + 出处可核验。
- **超级红线：少而精**——红线过多会被 Agent 当噪音创造性绕过。

## 六、多 Agent 与工具工程（阶段 2）

- **Orchestrator + Specialist 双层**：1 个 Orchestrator 负责拆解 / 调度 / 收敛；执行层是少数专精 Agent，只干一件事。
- **Spec 文件驱动协作**：Agent 间不靠对话传状态，靠共享 Spec / 计划文件接力，保证可回放 / 可审计 / 可续传。
- **MAST 14 种失败模式**：过度引入 Agent / 上下文共享污染 / 管理者瓶颈 / 错误级联放大 —— 与「Agent ≤3」结论一致。
- **ACI 清晰 + Poka-yoke 防呆**：工具 description 即契约，错误用法在 schema 层直接拦。
- **双循环隔离（在线 / 进化分离）**：线上 Agent 不得直接改正式逻辑，踩坑经验走离线 → Linter / 断言固化。
- **四种更新载体（优先低成本）**：知识 < Prompt+Skill < 程序+Harness < 参数——能下沉到更低成本载体就别动高层。

## 七、落地用法

- **阶段 2（结构设计）**：先满足 §一 WorkBuddy 特有约束，再按 §二 六要素对照缺哪补哪，最后按 §四 六支柱自检。
- **阶段 4（质量校验）**：把铁律写成可强制执行的 Linter / 门禁——本团已把「结构六要素」落成 `scripts/gates.py`，并入 `verify.py`。
- **阶段 5（审计）**：逐要素查「空壳」。
- **阶段 9（沉淀）**：把踩坑固化为 Linter / 断言，走离线进化。
