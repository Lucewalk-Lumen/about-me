# 交付保障

> 本团交付前的保障机制与失败处置纪律，供阶段 5–9 审计 / 放行 / 沉淀使用；主理人在收尾报告前强制执行。

## 一、执行率自检（SELF-AUDIT）

> 收尾报告发出前强制执行，最多 3 轮；任一 ❌ 回退对应阶段修复 → 重走验证 → 重检。

| 检查项 | 证据 |
|---|---|
| 端到端条目 ≥ 下限，且含 ≥1 条边界 / 异常路径（非仅 happy-path） | 实际条数 + 边界路径标注 |
| 必选功能全部可运行 | 逐条 |
| 安全红线清单全过 | 逐条 |
| 质量自审通过 | 逐条 |
| 校验含**原始输出** | 条数 |
| 不卡死计数 < 3 | 各诊断点 |
| 构建 / 编译 / 语法全通过 | 逐文件 |
| 修改阶段 CHECKPOINT 已输出 | 批次 |
| 备份及历史版本保留、临时文件已清理 | ls |
| 规划文件回读确认 + 状态已更新 | 逐项 |
| 不可逆操作（删 / 重命名）不单凭推断，须实实测复核 + 用户确认闸门 | 确认记录 |
| 关键决策已留痕（候选方案 / trade-off / 反选理由 / 撤销条件） | 决策记录片段 |
| 关键结论已构造反例尝试推翻（跑通 ≠ 正确） | 反例片段 / 证伪失败说明 |
| 任何改动须含真实驱动验证（真实执行 → 观测输出 → 断言）；禁以静态检查 / 肉眼替代 | 执行命令 + 原始输出 |
| 未为「通过」而放宽测试 / 断言 / 评分器；未把未验证结论写入持久状态 | 改动 diff + 红线对照 |
| 关键声明已逐条对证（声明 → 证据），未验证项已在已知限制中明示 | 声明清单 + 逐条证据 |
| 关键推理已外化为**可检查痕迹**；未外化的推理**不计入完成度** | 报告 / 交接块片段 |
| 报告口径基于本回合实际观察；失败 / 跳过 / 未验证项已按「第一句」披露 | 报告原文 + 逐条证据 |
| 交付物只含意图内文件；临时探针已删且**在原样状态重跑**验收 | 文件清单 + 重跑输出 |

**3 轮规则**：超出 3 轮 → 列出未修复项 + 原因 + 2–3 选项；5 分钟无回复 → 输出最终收尾（标未修复），不阻塞交付。

## 二、反例构造三步（证伪执行方法）

1. **识别不变量**——算法 / 结论依赖什么假设？（如：状态机不重复、计数不重不漏）
2. **构造违反不变量的输入**——空值 / 自环互环 / 并发写 / 超大输入 / 边界值（0 / 1 / 最大 / 负）。
3. **验证实现是否拒绝或正确处理**——遇到反例是崩溃、错误结果、还是正确处理？

## 三、交付信心门控（SELF-AUDIT 通过后、收尾前）

按「声明 → 证据」逐条对证，禁止用感觉冒充信心：

1. **列声明**：把关键声明拆成可验证项（需求满足 / 实现正确 / 校验通过 / 无回归 / 文档已同步）。
2. **找漏洞**：逐项自检——哪条声明最可能是假的？边界 / 失败路径 / 权限 / 并发 / 同类文件是否会打脸？
3. **修或披露**：P0 / P1 漏洞必须先修；低风险或外部不可控项在交付里明确披露，不得隐藏。
4. **跑证据**：为每条关键声明运行对应命令或检查。
5. **循环判定**：关键声明未验证、或存在未缓解 P0 / P1 → 继续处理；遇真实外部阻塞 → 证据化交接。
6. **事实上的 100%**：「当前可获得证据下，所有可运行验收均通过 + 所有已知高风险漏洞已修复 + 剩余风险已明示」，不等于绝对正确。

约束：已有证据覆盖当前制品即复用，不为每个标题重跑一套；不得把局部通过说成「完成 / 修复 / 100% 有信心」。

## 四、穷尽后的结构化失败报告

> 触发：已确认失败且标准处置清单全部完成仍未解决。不得写成「我不行」，它是问题边界的交接。

```text
## 结构化失败报告
- 已验证事实：{已实测确认的事实 + 证据来源}
- 已排除可能：{已排除的假设 + 排除依据}
- 缩小后的范围：{问题落在哪个文件 / 环节 / 数据流}
- 推荐下一步：{最小可行动作 + 执行命令}
- 交接信息：{精确位置 + 已改动项 + 回滚方式}
```

## 五、收尾报告模板

```text
📊 完成度: X% | 主线: {状态} | 产出: {摘要 ≤3 句} | 待办: {内容 / 无} | 下一步: {建议 ≤3 句}
```

- **完成度**：基于已验收 / 总功能 × 100%；无主线交付物时填 `N/A（元任务）`。量化强制：须带分子分母（已验证主线数 / 总主线数），只计入有验证证据的条目。
- **主线**：进行中 / 已完成 / 已中止；支线不计入。
- **产出**：1–3 句，含文件路径与验证方式。**待办**：无则填「无」。**下一步**：无则填「无」。

**写法**：先答后证、自含、术语已建立、禁对比式框架（「是 X 不是 Y」）、空洞词清零、代码与数字出散文、内容结束就停；失败 / 跳过 / 与预期不符放**第一句**；末段若是「我会…」→ 现在就去做。

## 六、抗合理化（出现下列念头即停手）

**收尾类**：

| 念头 | 现实 | 动作 |
|---|---|---|
| 「改动很小应该没问题」 | 小改动也必须给证据 | 补验证证据 |
| 「用户没提测试就不测了」 | 验证基线不因用户未要求而降低 | 补验证证据 |
| 「这个错误不影响主流程」 | 分支 / 边界错误也是未完成项 | 列入未完成项 |
| 「时间不够先这样交付」 | 未完成项必须列入待办 | 列入未完成项 |
| 「我检查过了没问题」（无证据） | 必须附命令 / 输出 / 清单 | 补验证证据 |
| 「跳过或后补验证」 | 无实测证据 = 未完成 | 补验证证据 |
| 「摘要 / 旧结论已验证过可直接引用」 | 摘要可能过时；引用前须回实据复核 | 回实据复核 |
| 「静态检查过了功能就正常」 | 有入口的改动必须真实驱动验证 | 补真实验证 |
| 「这一步本应产出 X」当作已产出 | 报告须基于本回合实际观察 | 补实测结果 |
| 把失败埋进结尾或并入「已完成」 | 失败须放报告第一句 | 改写报告 |
| 末段是「我会…」就结束回合 | 现在就去做 | 立即执行 |

**过程类**：把「懒得验证 / 无法验证 / 想快点交付 / 不该我管」包装成「合理理由」→ 按对应等级动作处理，如实写进收尾报告待办，不得静默降级。

## 七、确认超时默认规则

| 场景 | 默认行为 |
|---|---|
| 通用确认 | 5 分钟无回复 → 最保守 / 安全选项自动推进 |
| 破坏性操作（删除 / 覆盖 / 批量写） | **本规则优先**，一律不降级；有可靠备份且影响可局部化 → 走通用确认；否则 5 分钟无回复 → **默认取消**（保留备份可重试） |
| 规划确认 | 5 分钟无回复 → 默认推进 |
| 安全相关确认 | 一律等待用户明确回复，不自动推进 |

## 八、优雅中止（用户主动中止或不可恢复阻断）

1. **中止声明**：`[ABORT] 中止原因: ___; 当前阶段: ___; 已完成: ___ 项`
2. **保留回滚资产**：保留所有备份文件；规划文件标注 `状态: 已中止` + 中断点。
3. **清理临时文件**：删一次性临时脚本；**严禁删备份**。
4. **简化收尾**：`📊 完成度: X% | 主线: 已中止 | 产出: {已完成项} | 待办: {未完成项} | 下一步: {恢复方式}`

## 九、失败重试基线

| 失败类型 | 最大重试 | 说明 |
|---|---|---|
| 安全 / 数据类 | 0 | 立即升级不重试 |
| 语法 / 格式类 | 3 | — |
| 验证类失败 | 2 | — |
| 环境类失败 | 1 | 重试后升级 |
| 业务规则不明 | 0 | 向用户索取输入 |
| 网络 / 远程服务类 | 2 | 写操作前须确认幂等 |

**轮次与收敛**：默认循环 3 轮 / 安全最大 6 轮 / 每轮最大改动点 3；同一缺陷 2 轮未修复 → 标记已知限制；连续 2 轮仅低收益微调 → 建议提前结束。

## 十、未验证项强制披露

交付中凡无法验证、降级处理或长任务部分失败的条目，必须在「已知限制 / 未验证项 / 部分失败明细」中显式列出，禁止隐藏。四条硬约束：

- **缺口类型须标注**：每条注明缺口类型（无入口 / 无数据 / 环境不可达 / 未实测），不得只写「未验证」。
- **量词断言须附口径**：含「全部 / 均 / N 个 / 无残留」的断言须附枚举或全量实测口径（命令 + 命中数）；无口径则降级为抽样陈述。
- **未改断言**：把「不该改的没改」写成可核验断言（如「测试文件未修改」），禁默认省略。
- **探针与产物卫生**：临时探针按「造 → 用 → 删 → 在原样状态重跑验收」收尾；交付物混入范围外文件 ⇒ **重新生成**而非删掉了事。

## 十一、Go/No-Go 放行硬门控（阶段 7）

| 条件 | 判据 | 一票否决 |
|---|---|---|
| 官方校验器 | `verify.py --zip <包>.zip` exit 0 | 是 |
| 自建门禁 | `gates.py` + `dual_proof.py` + `quality_eval.py` 全部 exit 0 | 是 |
| P0 高危 | 全修复并复验通过 | 是 |
| 版本多处一致 | plugin.json == SKILL.md×N == contract.yaml == CHANGELOG == 脚本内嵌版本串 | 是 |
| 需求基线 | 交付物对「基线 + 变更条目」逐条核对通过 | 是 |
| 回滚预案 | 一键回滚命令已写入发布记录且可执行 | 否（缺失记 P1） |

任一「一票否决」项不过即 No-Go，不得放行；非一票否决项缺失记 P1，提审前必修。

## 十二、发布后观察期（灰度观测）

1. **观察期**：发布后 7 天为观察期，主理人每日复盘一次「是否有用户反馈驳回 / 报错」。
2. **观测项**：官方审核结果、市场安装报错、运行时异常、用户反馈。
3. **回滚触发**：观察期内出现 P0 级驳回或运行时崩溃，立即执行一键回滚命令，并回到阶段 1 重新诊断。

## 十三、落地用法

- **阶段 5（审计）**：反例构造三步 + 验证自检；SELF-AUDIT 表逐项过。
- **阶段 7（放行）**：Go/No-Go 放行硬门控 + 交付信心门控 + 收尾报告模板 + 未验证项强制披露。
- **阶段 8（版本）**：版本多处一致（含脚本内嵌版本串）。
- **发布后**：发布后观察期灰度观测，P0 触发回滚。
- **阶段 9（沉淀）**：把本轮抗合理化触发点与失败处置固化为门禁 / 清单，走离线进化。
