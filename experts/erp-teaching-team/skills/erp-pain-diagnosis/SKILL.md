# ERP 痛点诊断方法库

系统化的 ERP 痛点诊断工具集。**核心原则：区分"真痛"与"不习惯"，这决定了该改流程、该改系统，还是只需培训。**

## 使用时机

- 用户说 ERP "不好用"、"效率反而降了"、"大家都在用 Excel 绕路"
- 需要定位跨部门流程断点
- 需要判断某个环节该不该自动化
- 需要追查两个系统数据不一致的根因

## 一、断点识别分域检查表

逐域排查，找到断点位置。

### 销售域

- [ ] 销售开单后，仓库能否实时查到库存？（**最经典的断点**）
- [ ] 订单变更后，生产/采购是否收到通知？
- [ ] 销售承诺交期是否与实际产能/库存一致？
- [ ] 退货流程是否闭环？退货后库存是否自动回冲？
- [ ] 客户档案在销售、采购、财务三处是否重复录入？

### 采购域

- [ ] 采购申请 → 订单 → 到货 → 入库 是否全链路可追溯？
- [ ] 到货与质检是否分离？质检单是否自动生成？
- [ ] 供应商账期是否与付款审批联动？
- [ ] 采购价格是否与库存成本联动？（否则毛利算不准）
- [ ] 紧急采购是否有单独流程？（混在常规流程里会拖慢整体）

### 库存与仓储域

- [ ] 库存是否账实一致？差异多少？
- [ ] 批次/序列号管理是否覆盖全流程？
- [ ] 库存预警是否触发？（安全库存、呆滞库存）
- [ ] 盘点是否可执行？（不是只在系统里算账）
- [ ] 同一物料在多个仓库的调拨是否可追踪？

### 生产域

- [ ] BOM 版本是否唯一？是否有多版本混乱？
- [ ] 工单下达后，物料是否自动检查缺料？
- [ ] 领料、退料是否与工单绑定？
- [ ] 报工数据是否实时影响库存？
- [ ] 生产进度是否与订单交期联动？（否则插单没依据）

### 财务域

- [ ] 应收应付是否与业务单据自动关联？
- [ ] 对账是否还需要人工导出核对？
- [ ] 成本核算是否自动？是否有手工调整？
- [ ] 发票与订单、回款是否三单匹配？
- [ ] 财务是否成为所有报表的唯一出口？（若是，说明数据未在业务层收敛）

### 主数据域

- [ ] 物料编码是否一物一码？是否存在重复？
- [ ] 客户/供应商是否合并过重复主体？
- [ ] 单位换算是否统一？（pcs/箱/千克混用是常见坑）
- [ ] 组织架构与权限模型是否清晰？
- [ ] 谁有权修改主数据？修改是否留痕？

## 二、问题分类判据（最关键的一步）

**必须先分类，再定对策。误判会导致企业为错误的原因花掉预算。**

| 判断 | 识别方法 | 对策 | 反面案例 |
|------|----------|------|----------|
| **真痛** | 已在用 Excel/手工绕路，且有人抱怨 | 改流程或上系统 | 误判为不习惯 → 做了培训，问题依旧 |
| **不习惯** | 没人主动抱怨，只是觉得"别扭" | 培训 + 陪跑 | 误判为真痛 → 改系统、二开，浪费预算 |
| **能力不足** | 想做但没人会 | 先培训再谈自动化 | 误判为技术问题 → 上了自动化，没人会用 |
| **利益冲突** | 某部门靠此环节掌握信息优势或审批权 | 管理层强制推动 | **系统解决不了**，硬上只会加剧对抗 |
| **口径冲突** | 两系统同名字段含义不同 | 先统一口径 | 误判为数据错误 → 反复清洗，永远不干净 |

**追问清单**（判断用）：

1. "现在大家用什么办法绕过这个问题？" → 有绕路方案 = 真痛
2. "如果不改，最坏会怎样？" → 答不上来 = 可能是不习惯
3. "这个环节是谁在负责？他会同意改吗？" → 抗拒且有理由 = 利益冲突
4. "A 系统和 B 系统里这个字段，含义一样吗？" → 不一样 = 口径冲突

## 三、优先级评分公式

```
优先级得分 = (改造收益 × 发生频次) / 实施成本
```

| 维度 | 取值参考 |
|------|----------|
| **改造收益** | 每月节省工时 + 减少的差错成本 |
| **发生频次** | 每日 > 每周 > 每月 > 每季 |
| **实施成本** | 需改环节数 × 涉及部门数 |

**注意**：按"哪个最值得改"排序，不是按"哪个最痛"排序。**最痛的地方未必最值得改** —— 如果成本极高，绕过去更划算。

## 四、根因追问顺序（数据不一致类）

**顺序不能颠倒** —— 跳过第一步会做无用功。

```
1. 定义检查：字段定义是否一致？（口径问题优先于数据问题）
      ↓ 一致
2. 来源检查：数据从哪来？手工录入还是接口同步？
      ↓
3. 时点检查：什么时候开始错的？当时有什么变更？
      ↓
4. 权限检查：谁能改？改动是否留痕？
      ↓
5. 责任检查：录入的人知道自己的错了吗？有校验吗？
```

**核心判断**：如果两个系统字段定义不同，那不是数据错误，是设计缺陷。**任何清洗都是徒劳的，必须先统一口径。**

## 五、诊断输出格式

```
【诊断结论】N 个断点，其中 M 个高危
根因：<30 字内>

【断点清单】
| 编号 | 位置 | 现象 | 频次 | 涉及部门 | 类型 |

【证据链】每个判断的依据；证据不足标注"需确认"

【优先级排序】按公式得分

【阻力预警】哪些环节有人为抵抗，属哪种类型
```

## 六、反面案例库（典型失败情景；口径以 `references/pitfalls.md` 为准）

| 案例 | 根因 | 教训 |
|------|------|------|
| 花千万替换 Oracle，国产 ERP 上线半年出不来合格报表 | 旧系统标准数据从未捋顺 | 数据治理必须前置 |
| 上线后业务部门集体抵制 | 把"不习惯"当成"真痛"改了系统 | 先判断类型再动手 |
| "以前互相甩锅，现在有 ERP 了，全是系统错" | 无唯一流程 Owner | 责任机制必须先定 |
| 员工离职后流程无人接续 | 流程未文档化 | 知识沉淀是上线的前提 |
| 培训做了，考核不挂钩，无人使用 | 培训与激励脱钩 | 关键用户考核必须挂钩 |
| 账实不符，加人手盘点 | 未从流程上找原因 | 治标不治本 |

## 七、快速诊断提问脚本

当用户描述模糊时，按此顺序追问（**最多问三个，不要一次问十个**）：

1. **系统**："你现在用的是什么系统？SAP / Oracle / 用友 / 金蝶 / 自研 / 其他？"
2. **角色规模**："团队多少人？你是什么角色 —— 老板 / IT / 实施 / 一线操作？"
3. **具体痛点**："最让你头疼的那一件具体事情是什么？"

**不要问**："能否详细描述一下你的业务场景和需求？" —— 这种问题会让用户不知道从哪说起。

## 内容边界

本文件列举的厂商名称仅作提问示例，**不代表对其能力或市场地位的判断**。

学生问"某某系统能不能做到 X"时，**不凭记忆答**，应查厂商官方文档。
