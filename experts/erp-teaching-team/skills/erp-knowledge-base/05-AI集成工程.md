# AI 集成：架构、工具函数与 RAG 工程

> **本篇为自建内容。** 集成架构与 Clean Core 理念为行业共识，代码模板、RAG 参数、踩坑清单为本团重写，**经本团推演与案例推敲，未经本团项目实证**。

## 铁律

| # | 铁律 | 理由 |
|---|---|---|
| 1 | **AI 层不碰数据库事务** | 事务逻辑统一收敛至 ERP 业务层 |
| 2 | **AI 只做两件事** | 调工具函数（写）、走 RAG 检索（读） |
| 3 | **门面式解耦** | AI 模块经 Facade 调业务层，不直接注入 Service/Mapper |
| 4 | **写操作必须二次确认** | ERP 错误写操作是真金白银的损失 |
| 5 | **不编造** | RAG 仅依据内部文档作答，答案末尾标注来源 |
| 6 | **AI 不绕过内控与审批** | 红线，不可协商 |
| 7 | **主数据先行** | 主数据不统一，集成就是"把脏数据同步得更快" |
| 8 | **Clean Core 优先** | AI 作为可插拔能力，不侵入记录系统 |

## 一、Clean Core：AI 集成的架构前提

**如果 AI 改动了核心表结构，三年后就是升级噩梦。**

| 概念 | 含义 |
|---|---|
| **记录系统 SoR** | 财务核心、总账等**保持稳定**，不因 AI 改造而动 |
| **差异化系统 SoE** | AI 层、电商、制造执行等**灵活拼装**，独立演进 |
| **Clean Core** | 核心保持干净，AI 作为可插拔能力挂外围 |

| 做法 | 结果 |
|---|---|
| AI 直接改核心表结构 | 升级噩梦，AI 一动全盘崩 |
| AI 作为 SoE 挂外围 | 核心稳定，AI 独立升级 |
| AI 侵入 SoR | **最危险** —— AI 的不确定性会污染账务真实性 |

**账务真实性一票否决**：任何"为报表好看而调数""绕过审批直接过账"的措施一律否决。**ERP 的账是给审计和稽查看的，不是给面子看的。**

## 二、三种接法的边界

| 接法 | 适用条件 | 风险 | 建议 |
|---|---|---|---|
| **API 直连** | 厂商开放 API 且文档完整 | 依赖厂商版本节奏 | 首选 |
| **只读库 + RPA** | 无 API，仅需读数据 | 写操作仍需 RPA 兜底 | 次选 |
| **RPA 兜底** | 老系统完全无接口 | 界面变动即失效 | 尽量避免 |

**判断流程**：
```
厂商有开放 API 且文档完整？
  ├─ 是 → API 直连（首选）
  └─ 否 → 只需读数据？
            ├─ 是 → 只读库
            └─ 否（需要写）→ 必须 RPA
```

### 关键设计点

| 设计点 | 做法 | 理由 |
|---|---|---|
| 门面模式 | AI 经 `Facade` 调业务层 | AI 改不动业务逻辑 |
| 预留 Feign | 架构上预留微服务接口 | 未来拆分时 AI 层代码无需改动 |
| **单体优先** | 单工程 + 门面隔离 | **中小企业 IT 运维能力有限** |
| 同库向量 | pgvector 与业务数据同库 | 减少运维，检索时可 JOIN |

### 单体 vs 微服务：诚实的建议

| 场景 | 建议 |
|---|---|
| < 200 人 | **单体 + 门面隔离**，不要微服务 |
| 200-1000 人 | 单体起步，预留 Feign |
| > 1000 人 / 多组织 | 可考虑微服务，仍需评估运维能力 |
| **IT 团队 < 5 人** | **不要上微服务 + K8s**，运维成本会压垮团队 |

### 六条设计要求

1. **description 写清业务语义** —— AI 靠它决定是否调用、怎么传参
2. **参数必须有 `@ToolParam` 描述** —— 说明格式和示例
3. **只暴露必要能力** —— 内部方法不暴露给 AI
4. **写操作必须可确认** —— 返回前让用户确认，不静默执行
5. **返回结构化结果** —— 便于 AI 理解并复述
6. **异常转人类可读提示** —— 不要把堆栈抛给 AI

## 五、RAG 知识库工程

### 四个关键决策

| 决策点 | 正确做法 | 常见错误 |
|---|---|---|
| **分片大小** | 默认 300-500 字，**保证语义完整** | 机械按固定字符数切断句子 |
| **切分方式** | 优先按文档结构自动生成（段落/标题） | 硬切导致上下文断裂 |
| **检索策略** | 问题向量化 + 相似度检索，**返回 Top-N** | 全库检索塞满上下文 |
| **过滤机制** | 自定义相似度阈值 | 无阈值，召回一堆无关文档 |

### 文档处理流程

```
上传 PDF / Word / TXT / Markdown
  ↓
解析（Apache Tika）→ 过滤页眉页脚空白乱码 → 提取纯文本
  ↓
分片（按结构，300-500 字，携带元数据）
  ↓
向量化（bge-m3）→ 存入 PgVector
  ↓
支持：全量重建 / 增量新增 / 无效向量清理
```

### 分片元数据（必写，否则无法溯源）

```json
{
  "docId": "DOC-2026-001",
  "docName": "采购流程文档.pdf",
  "category": "采购",
  "uploadTime": "2026-10-01",
  "chunkIndex": 7,
  "chunkTotal": 42
}
```

### 提示词模板

```
检索增强 + 用户问题

大模型仅依据内部文档作答，禁止编造企业制度、数据，
回答末尾标注引用来源。
```

### 必须支持的交互能力

- 同步问与流式打字两种输出格式
- 检索超时、重试、日志记录
- 检索失败时友好降级（明确告诉用户"没找到相关文档"）

## 六、模型选型与私有化部署

| 用途 | 推荐模型 | 部署 |
|---|---|---|
| 开发 / 小规模生产 | qwen2.5:7b + bge-large-zh | 本地 Ollama |
| 中等生产 | qwen2.5:7b 主力 + bge-m3 | 本地集群 |
| **敏感数据** | 全私有化 | **数据不出内网** |

**资源换算**：qwen2.5:7b 运行需约 8-10GB 内存，生产环境建议至少 32GB。换 32B 模型需显著更多资源，**不建议中小企业尝试**。

**调用方式**：私有化 Qwen 走 Ollama 接口，Spring AI 直接对接；对外输出 OpenAI 标准格式便于切换。

**诚实说明局限**：7B 模型在"检索 + 模板化回答"场景优秀，在"复杂多步推理"需要更强模型。**不要承诺它能做到 90 分以上。**

## 七、踩坑清单

| 坑 | 现象 | 解法 |
|---|---|---|
| **分片硬切** | 回答断章取义 | 按结构分片，不用固定字数 |
| **无元数据** | 召回后无法溯源 | 元数据必写 |
| **无阈值过滤** | 上下文被无关文档污染 | 设相似度阈值 |
| **AI 直连 Mapper** | AI 一改就破坏业务逻辑 | 强制门面隔离 |
| **写操作无确认** | AI 误操作造成真实损失 | 写操作必须确认 |
| **数据未治理就上 AI** | 输出错误结论，比不做更糟 | 先做数据就绪度评估 |
| **上下文缺失** | 项目无法交付价值 | **这是首要失败原因** |
| **微服务过度设计** | 运维成本压垮小团队 | 单体 + 门面隔离起步 |
| **模型能力高估** | 期待 7B 做复杂推理 | 诚实界定边界 |

## 八、最关键的一条

> **Agent 的能力上限，取决于它所能获取的上下文质量。缺乏上下文是企业 AI 项目无法交付价值的首要原因。**

**这意味着**：设计架构之前，先确认数据治理已到位。**架构再好，数据脏乱，产出的一定是错误答案。**

数据就绪度评估方法见 `./01-AgenticERP与2026现状.md`。

## 九、给教师的话

**建议教学顺序**：铁律 → 铁律 1（AI 不碰数据库）的反例 → 门面隔离代码 → RAG 四决策 → 踩坑清单

**最值得讲的是踩坑清单** —— 学生自己踩过一遍，比听十遍规则记得牢。

**动手环节**：让学生把自己的一个真实业务场景写成 `queryXxx` 工具函数，标出哪些是读、哪些必须加确认。
