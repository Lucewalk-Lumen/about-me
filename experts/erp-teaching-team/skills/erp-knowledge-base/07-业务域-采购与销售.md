# 业务域深度（一）：采购 P2P 与销售 O2C

> **本篇为自建内容。** 采购与销售是断点最高发的一线，也是 AI 集成最容易见效的入口。

## 一、采购域 P2P（Procure-to-Pay）

### 全链路七步

```
采购申请 Requisition → 寻源 Sourcing → 合同 Contract
→ 采购订单 PO → 收货 GR → 发票校验 → 付款 Payment
```

**核心原则**：每一环都应有凭证，链条不断。**断在哪一环，账就断在哪一环。**

### 关键控制点

| 环节 | 控制点 | 失控后果 |
|---|---|---|
| 采购申请 | 预算占用、超预算审批 | 超预算采购、期末突击花钱 |
| 寻源 | 至少三家比价、供应商资质 | 单一供应商依赖、价格失控 |
| 采购订单 | 价格与合同一致、交期确认 | 合同外采购、事后追认 |
| 收货 | 质检合格才入库 | 收料不检验、退货成本转移给供应商 |
| 发票校验 | **三单匹配**（见下） | 付款给错单、重复付款 |
| 付款 | 付款条件与合同一致 | 提前/超额付款、资金计划失真 |

### SRM（供应商关系管理）

**采购的深层能力在供应商管理，不在下单。**

| 能力 | 做什么 | 为什么重要 |
|---|---|---|
| **供应商分级** | 按质量、交付、价格、响应分为 A/B/C/D | 采购份额分配的依据 |
| **供应商绩效评估** | 准时交付率、质量合格率、响应时长 | 决定是否淘汰或扶持 |
| **供应商准入** | 资质、财务、产能、合规审查 | **避免单一供应商卡脖子** |
| **供应商协同** | 预测共享、产能协商、联合改进 | 降库存、降成本 |
| **供应商门户** | 供应商自助查订单、报产能、收对账 | 减少采购跟单工作量 |

**常见断点**：
- 供应商在 Excel 里维护产能和交期，采购要打电话问 —— **数据不入系统，上游是黑的**
- 采购比价表离线维护，系统里只有最终结果 —— **过程不可追溯，无法审计**
- 供应商考核靠采购员印象 —— **换人就换评价**

### 三单匹配（Three-Way Match）

**这是采购内控的核心机制。**

```
采购订单（PO）  ⇄  收货单（GR）  ⇄  供应商发票（Invoice）
     数量/价格一致      数量/质量一致      金额一致
```

| 匹配结果 | 系统动作 |
|---|---|
| 三单一致 | 允许付款 |
| 数量/价格不一致 | **冻结，挂起待处理** |
| 发票有、收货无 | **拒绝付款**（可能是虚假发票） |
| 收货有、发票未到 | 暂估入账（GR/IR） |

**三单匹配的价值**：把"人盯发票"变成"系统卡发票"，**不依赖采购员的自觉**。

**为什么是 AI 集成的首选场景**：匹配逻辑规则明确、重复性高、错了有后果 —— 适合自动化，且**必须有系统控制，不该交给 AI 判断**。

### 采购的 AI 机会

| 场景 | 可行性 | 说明 |
|---|---|---|
| 发票与订单匹配 | 高 | 规则明确，AI 辅助抽取信息，系统做校验 |
| 供应商报价比对分析 | 高 | 多维数据聚类，非线性定价识别 |
| 交期风险预警 | 中 | 需历史交期数据支撑 |
| 采购品类策略建议 | 中 | 需品类管理数据 |
| 供应商选择 | 低 | **涉及商业判断，不该交给 AI** |

## 二、销售域 O2C（Order-to-Cash）

### 全链路八步

```
线索 Lead → 报价 Quote → 订单 Order → 信用检查 Credit
→ 发货 Ship → 开票 Invoice → 应收 AR → 收款 Collection
```

**销售域的核心不是卖出货，是"钱能收回来"。**

### 关键控制点

| 环节 | 控制点 | 失控后果 |
|---|---|---|
| 报价 | 折扣权限、价格底线 | 越权低价、利润流失 |
| 订单 | 交期承诺（ATP 可用量校验） | **承诺了交不出的货 → 最经典的失信源** |
| 信用检查 | 信用额度、逾期天数 | 发出去了收不回钱 |
| 发货 | 拣货复核、出库确认 | 错发漏发、库存不准 |
| 开票 | 与发货单匹配 | 未发先开票、税务风险 |
| 应收 | 账期、逾期预警 | 应收账款变成坏账 |
| 收款 | 与应收核销 | 收款挂不上账，账实不符 |

### ATP 可用量（Available to Promise）

**销售最该盯的数字。**

```
ATP = 现有库存可用量 + 在途量 + 可用产能 − 已承诺量
```

**为什么关键**：销售答应客户"三周后到货"时，凭的是什么？**必须凭 ATP，不能凭感觉。**

| 常见问题 | 后果 |
|---|---|
| 承诺时未校验 ATP | 交期违约、客户流失 |
| ATP 算的是全部库存，未扣已承诺 | 同一批货被承诺给多个客户 |
| 未考虑在途采购的延迟 | 纸面上有货，实际到不了 |

**ATP 是断点重灾区** —— 典型现场:"销售开单后仓库查不到库存"，本质是**销售与仓库对可用量的口径不一致**。

### 销售的 AI 机会

| 场景 | 可行性 | 说明 |
|---|---|---|
| 报价单生成、历史价格参考 | | 重复性高，AI 辅助 |
| 客户信用风险评分 | | 基于历史回款数据 |
| 交期预测与承诺建议 | | 需历史交期 + 产能数据 |
| 需求预测与备货建议 | | 需稳定数据积累 |
| 客户流失预警 | | 需外部数据 + 交互记录 |
| 客户定价谈判 | 低 | **商业判断，不交给 AI** |

## 三、两个域的共同断点（诊断重点）

**从一线反馈看，P2P 与 O2C 的断点高度集中在四处：**

| 断点 | 表现 | 根因 | 对策 |
|---|---|---|---|
| **主数据不一致** | 同一物料/客户在两系统不同名 | 编码规则缺失或未统一 | **先治理主数据** |
| **单据重复录入** | 采购在 Excel 下单、仓库在系统录单 | 两系统未打通 | 建集成或 RPA |
| **审批不在系统里** | 微信/邮件批完再补录 | 流程设计缺失 | **审批必须进系统** |
| **对账在系统外** | 月底手工核对付款 | 缺少三单匹配机制 | 上三单匹配 |

**特别提醒：审批不在系统里是最危险的。** 它意味着系统数据不能反映真实业务状态 —— **所有报表都建立在残缺数据上**。

## 四、给教师的话

**本篇的教学价值在"控制点"这个概念。**

- 学生最常见误区：**以为买了 ERP 就控住了风险**。实际上控制点必须逐环设计，漏一环就白上
- **三单匹配是最值得讲的机制** —— 简单、可理解、立刻见效，且体现"用系统替代人盯"
- **ATP 概念重要但常被忽略** —— 建议结合"承诺了交不出的货"这个真实场景讲
- 教学时可让学生画自己公司的 P2P/O2C 流程，标出哪些环节在系统外

**常见学生误区**：把"上系统"等同于"上流程"。**流程不变，系统再好也是空转。**

## 声明

本篇为教学材料，流程与控制点为通用最佳实践。**具体厂商的实现方式可能不同**；涉及税务、会计准则的处理须以引用当日官方规定为准，本篇不提供税务结论。
