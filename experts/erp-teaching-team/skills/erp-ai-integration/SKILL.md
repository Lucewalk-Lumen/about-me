# ERP + AI 集成技术资产库

编写时验证过的 ERP Agent 集成方案与代码模板。**核心红线：AI 层不处理数据库事务，所有数据操作收敛至 ERP 业务层。**

## 使用时机

- "AI 怎么接进我的 ERP 系统？"
- "帮我设计 ERP Agent 架构"
- "工具函数怎么写？"
- "RAG 知识库怎么做？分片多大？"
- "用公有云 API 还是私有化部署？"

## 一、技术铁律

| # | 铁律 | 理由 |
|---|------|------|
| 1 | **AI 层不碰数据库事务** | 事务逻辑统一收敛至 ERP 业务层，避免 AI 造成数据不一致 |
| 2 | **AI 只做两件事** | 调工具函数（写）、走 RAG 检索（读）。不做其他操作 |
| 3 | **门面式解耦** | AI 模块通过 Facade 调用业务层，不直接注入 Service/Mapper。AI 改不动业务逻辑 |
| 4 | **写操作必须二次确认** | ERP 里的错误写操作是真金白银的损失 |
| 5 | **不编造** | RAG 场景仅依据内部文档作答，答案末尾标注引用来源 |
| 6 | **AI 不绕过内控与审批** | 红线。AI 产出不得跳过任何审批节点 |
| 7 | **主数据先行** | 物料/客户/供应商/科目主数据不统一，集成就是"把脏数据同步得更快" |
| 8 | **Clean Core 优先** | AI 层作为差异化可插拔能力，不侵入核心记录系统（SoR） |

## 三、Clean Core 与后现代 ERP 理念

**这是 AI 集成的架构前提。** 详见 `skills/erp-knowledge-base/05-AI集成工程.md`。

| 概念 | 含义 |
|---|---|
| **记录系统 SoR** | 财务核心、总账等**保持稳定**，不因 AI 改造而动 |
| **差异化系统 SoE** | AI 层、电商、制造执行等**灵活拼装**，独立演进 |
| **Clean Core** | 核心保持干净，AI 作为可插拔能力挂外围 |

### 为什么这决定了 AI 集成的成败

| 做法 | 结果 |
|---|---|
| AI 直接改核心表结构 | 升级噩梦，AI 一动全盘崩 |
| AI 作为 SoE 挂外围 | 核心稳定，AI 独立升级 |
| AI 侵入 SoR | **最危险** —— AI 的不确定性会污染账务真实性 |

**账务真实性一票否决**：任何"为报表好看而调数""绕过审批直接过账"的措施一律否决。**ERP 的账是给审计和稽查看的，不是给面子看的。**

### 关键设计点

| 设计点 | 做法 | 理由 |
|--------|------|------|
| 门面模式 | AI 模块经 `Facade` 调业务层 | AI 改不动业务逻辑，降低上线风险 |
| 预留 Feign | 架构上预留微服务接口 | 未来拆分时 AI 层代码无需改动 |
| **单体优先** | 单工程 + 门面隔离 | 中小企业 IT 运维能力有限，**不要一上来就上微服务** |
| 模型分工 | 主智能体 / RAG / Embedding 可分离 | 7B 级别可覆盖多数企业场景 |

### 单体 vs 微服务：诚实的建议

| 场景 | 建议 |
|------|------|
| < 200 人企业 | **单体 + 门面隔离**，不要微服务 |
| 200-1000 人 | 单体起步，预留 Feign 接口，确有需要再拆 |
| > 1000 人 / 多组织 | 可考虑微服务，但仍需评估运维能力 |
| **任何规模** | 若 IT 团队少于 5 人，**不要上微服务 + K8s**，运维成本会压垮团队 |

## 五、三种接法的边界判断

| 接法 | 适用条件 | 风险 | 建议 |
|------|----------|------|------|
| **API 直连** | 厂商开放 API 且文档完整 | 依赖厂商版本节奏 | 首选 |
| **只读库 + RPA** | 无 API，仅需读数据 | 写操作仍需 RPA 兜底 | 次选 |
| **RPA 兜底** | 老系统完全无接口 | 界面变动即失效，维护成本高 | 尽量避免，但正视其不可替代性 |

**判断流程**：
```
厂商有开放 API？
  ├─ 有 → API 直连（首选）
  └─ 无 → 只需读数据？
            ├─ 是 → 只读库
            └─ 否（需要写）→ 必须 RPA
```

## 六、业务工具函数设计规范

### 典型业务域划分（参考 14 个函数）

| 业务域 | 工具函数示例 | 读/写 |
|--------|-------------|-------|
| 库存 | `queryStock` 查库存、`checkLotTrace` 批次追溯、`lockStock` 锁定库存 | 读 / 写 |
| 采购 | `queryPurchaseOrder` 查采购单、`createPurchaseReq` 建采购申请 | 读 / 写 |
| 销售 | `querySalesOrder` 查销售单、`checkDeliveryStatus` 查交付状态 | 读 |
| 生产 | `queryBom` 查 BOM、`queryWorkOrder` 查工单、`checkMaterialShortage` 查缺料 | 读 |
| 财务 | `queryReceivable` 查应收、`queryPayable` 查应付 | 读 |
| 主数据 | `queryMaterial` 查物料、`querySupplier` 查供应商 | 读 |

### 门面隔离 + 写操作确认的标准写法

> [!] **本节是工具函数代码的唯一权威源**。知识库 `05-AI集成工程.md` 只讲教学要点并指向本节；修改代码只改这里。

```java
@Component
public class ErpToolFacade {

    @Resource
    private ErpBusinessService erpBusinessService;  // 业务层，非 Mapper

    @Tool(description = "查询指定物料的实时可用库存")
    public StockResult queryStock(
        @ToolParam(description = "物料编码，如 ZL001") String materialCode,
        @ToolParam(description = "仓库编码，不传则查全部仓库") String warehouseCode) {
        try {
            return erpBusinessService.queryStock(materialCode, warehouseCode);
        } catch (BizException e) {
            throw new ToolException("库存查询失败：" + e.getMessage());
        }
    }

    @Tool(description = "创建采购申请单。执行前必须向用户确认")
    public PurchaseReqResult createPurchaseReq(
        @ToolParam(description = "物料编码") String materialCode,
        @ToolParam(description = "采购数量") int quantity,
        @ToolParam(description = "期望到货日期，格式 yyyy-MM-dd") String expectDate) {

        // 写操作铁律：必须先让用户确认
        PurchaseDraft draft = erpBusinessService.buildDraft(materialCode, quantity, expectDate);
        return PurchaseReqResult.needsConfirm(draft, "确认创建采购申请？");
    }
}
```

### 六条设计要求

1. **description 写清业务语义** —— AI 靠它决定是否调用、怎么传参
2. **参数必须有 `@ToolParam` 描述** —— 说明格式和示例
3. **只暴露必要能力** —— 内部方法不要暴露给 AI
4. **写操作必须可确认** —— 返回前让用户确认，不静默执行
5. **返回结构化结果** —— 便于 AI 理解并向用户复述
6. **异常转人类可读提示** —— 不要把堆栈抛给 AI

## 七、RAG 知识库工程

### 四个关键决策

| 决策点 | 正确做法 | 常见错误 |
|--------|----------|----------|
| **分片大小** | 默认 300-500 字，**保证语义完整** | 机械按固定字符数切断句子 |
| **切分方式** | 优先按文档结构自动生成（段落/标题） | 硬切导致上下文断裂 |
| **检索策略** | 问题向量化 + 相似度检索，**返回 Top-N** | 全库检索塞满上下文 |
| **过滤机制** | 自定义相似度阈值，过滤低相关片段 | 无阈值，召回一堆无关文档 |

### 文档处理流程

```
上传 PDF / Word / TXT / Markdown
  ↓
解析（Apache Tika）→ 过滤页眉页脚空白乱码 → 提取纯文本
  ↓
分片（按结构，300-500 字，携带元数据）
  ↓
向量化（bge-m3）→ 存入 PgVector
  ↓
支持：全量重建向量 / 增量新增向量 / 无效向量清理
```

### 分片元数据（必写，否则无法溯源）

```json
{
  "docId": "DOC-2026-001",
  "docName": "采购流程文档.pdf",
  "category": "采购",
  "uploadTime": "2026-10-01",
  "chunkIndex": 7,
  "chunkTotal": 42
}
```

### 提示词模板

```
检索增强 + 用户问题

大模型仅依据内部文档作答，禁止编造企业制度、数据，
回答末尾标注引用来源。
```

### 必须支持的交互能力

- 同步问与流式打字两种输出格式
- 检索超时、重试、日志记录
- 检索失败时友好降级（明确告诉用户"没找到相关文档"）

## 八、模型选型与私有化部署

| 用途 | 推荐模型 | 说明 |
|------|----------|------|
| 开发 / 小规模生产 | qwen2.5:7b + bge-large-zh | 7B 级别，指令遵循与语义向量化兼顾 |
| 中等生产 | qwen2.5:7b 主力 + bge-m3 | 分离主模型与 Embedding |
| 敏感数据场景 | 全私有化本地部署 | 数据不出内网 |

**部署方式**：私有化 Qwen 走 Ollama 接口，Spring AI 直接对接；对外输出 OpenAI 标准格式模型便于切换。

**诚实说明局限**：7B 模型的能力有边界，不要承诺它能做到复杂推理任务的 90 分以上。**它在"检索 + 模板化回答"场景表现优秀，在"复杂多步推理"场景需要更强的模型。**

## 九、踩坑清单（典型失败情景；口径以 `references/pitfalls.md` 为准）

| 坑 | 现象 | 解法 |
|----|------|------|
| **分片硬切** | 回答断章取义、语义不完整 | 按文档结构分片，不用固定字数 |
| **无元数据** | 召回后无法溯源，用户不信任 | 元数据必写 |
| **无阈值过滤** | 召回一堆无关文档污染上下文 | 设相似度阈值 |
| **AI 直连 Mapper** | AI 一改就破坏业务逻辑 | 强制门面隔离 |
| **写操作无确认** | AI 误操作造成真实损失 | 写操作必须确认 |
| **数据未治理就上 AI** | 输出错误结论，比不做更糟 | 先做数据就绪度评估 |
| **上下文缺失** | 项目无法交付价值 | **这是首要失败原因**，见下方 |
| **微服务过度设计** | 运维成本压垮小团队 | 单体 + 门面隔离起步 |
| **模型能力高估** | 期待 7B 做复杂推理 | 诚实界定能力边界 |

## 十、最关键的一条

> **Agent 的能力上限，取决于它所能获取的上下文质量。缺乏上下文，是企业 AI 项目无法交付价值的首要原因。**

**这意味着**：在设计架构之前，先确认数据治理已到位。**架构再好，数据脏乱，产出的也一定是错误答案。** 数据就绪度评估是 AI 集成的**前置门禁**。
